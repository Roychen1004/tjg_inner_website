# 00 — 網站目的與範圍

> 鐵正綱工程 內部管理系統（TJG Inner Website）
> 版本 v0.1｜2026-08-01｜狀態：**待確認**

---

## 1. 一句話定義

> **把《成本管理總作業手冊》的制度，變成每天真的會用的系統。**

讓管理人員在同一個地方，看見並調度**人力、資金、採購、進度**——而不是在 Excel、紙本與 LINE 之間拼湊。

---

## 2. 為什麼要做

### 2.1 公司已經有制度，但制度沒有載體

《鐵正綱_成本管理總作業手冊》定義了非常完整的成本管理體系：

- **六大成本階段**：原物料採購 → 入庫驗收 → 生產準備 → 加工製造 → 品質檢驗 → 成品交付
- **18 項 KPI**：OEE、材料利用率、換線時間、庫存週轉率、OTD 準時交貨率⋯（附錄 A）
- **8 組成本公式**：真實時薪、製造費用率、完全成本、品質成本 PAF⋯（附錄 B）

但手冊裡的每一個公式，都需要**資料**才能算。目前沒有系統在收集這些資料，所以：

> 手冊第 3 章：「不能衡量，就不能管理。」
> 現況是——**制度寫得出來，數字算不出來。**

### 2.2 手冊自己診斷出的問題

手冊第 6.3 節列出六大隱性成本，合計**逾 1,200 萬／年**，相當於顯性營運成本的 14%：

| 隱性成本 | 年度估算 | 為何失控 |
|---|---:|---|
| 品質失敗成本 | ~462 萬 | 重工／報廢／客訴分散，難統計 |
| OEE 效率缺口 | ~210 萬 | 未量測設備閒置損失 |
| 換線整備時間 | ~170 萬 | 視為理所當然的損耗 |
| 交付失敗 | ~162 萬 | 罰款與商譽損失低估 |
| 過度檢驗 | ~105 萬 | 誤以為檢驗越多越好 |
| 庫存資金占用 | ~101 萬 | 不在費用科目，是機會成本 |

**這六項的共同點：全都不在帳本上，全都沒有人在追蹤。**

### 2.3 POC 已經驗證了流程模型

`POC/鐵正綱_營運儀表板.jsx` 證明了一件重要的事：**鐵正綱的工作是雙軌並行的**。

一個專案走一條主線（接案→設計→報價→採購→施工→驗收→結案），但底下同時有很多批構件各自在不同環節（有的在加工、有的送外廠噴砂、有的已經進場安裝）。這個模型是對的，但 POC 的資料存在瀏覽器裡，**關掉就沒了、換台電腦就看不到、沒有帳號權限、沒有歷史紀錄**。

## 4. 誰會用這個系統

| 角色 | 人數估計 | 主要裝置 | 每天用它做什麼 |
|---|---|---|---|
| 經營者／老闆 | 1–2 | 桌機、手機 | 看全公司在哪裡卡住、錢收得回來嗎 |
| 廠長／生產經理 | 1–2 | 桌機 | 排產、看批次卡在哪一站、產線狀態 |
| 工地主任 | 2–4 | **手機** | 回報工項進度、分包商到工、現場問題 |
| 專案負責人 | 3–5 | 桌機、手機 | 追自己負責的案子、對客戶交代 |
| 採購 | 1–2 | 桌機 | 請購、詢比議、追料到廠沒 |
| 品保 | 1–2 | 平板、桌機 | 進料檢驗、製程檢驗、不良處理 |
| 會計／財務 | 1–2 | 桌機 | 請款、應收應付、成本核算 |
| 人資／行政 | 1 | 桌機 | 出勤、請假、薪資、簽核 |
| 廠內師傅 | 10–20 | **手機** | 回報加工進度、領料、報工 |

**總計約 25–50 人**，其中**現場人員（工地主任＋師傅）約占一半，且主要用手機**——這是設計上必須先照顧的族群。

## 5. 成功衡量指標

不是「系統做完了」就算成功。以下是**可驗證**的指標：

### 第一階段（P1，進度追蹤）

| 指標 | 現況 | 目標 | 怎麼量 |
|---|---|---|---|
| 進度資訊延遲 | 週會才知道（3–7 天） | **≤ 1 個工作日** | 比對階段異動時間 vs 實際發生時間 |
| 「需要關注」清單來源 | 靠廠長記憶 | **100% 系統自動產生** | 系統可列出所有 atrisk／delayed 項目 |
| 階段異動可追溯性 | 無紀錄 | **100% 有紀錄**（誰、何時、備註） | 抽查 20 筆異動，都查得到 |
| 請款時機辨識 | 出貨後常隔數週才想起 | **出貨進場當日自動標記可請款** | 比對出貨日 vs 可請款標記日 |
| 實際使用率 | — | **≥ 3 種角色每日登入使用** | 登入紀錄 |

### 後續階段（P2–P4，對應手冊 KPI）

| 指標 | 手冊現況 | 手冊目標 | 對應階段 |
|---|---|---|---|
| 庫存週轉率 | 4 次／年 | ≥ 6 次／年（釋放約 833 萬現金） | P2 |
| 資金收攏率 | — | 建立可視化並持續提升 | P2 |
| OEE 設備總效率 | 60% | ≥ 75%（等同增加 1,200 萬產能） | P3 |
| 平均換線時間 | — | ≤ 30 分鐘 | P3 |
| 品質預防成本占比 | 8% | ≥ 15% | P3 |
| 準時交貨率 OTD | — | ≥ 98% | P3 |
| 六大隱性成本可視化 | 0 項 | **6 項全部有數字** | P2–P3 |

> **最重要的一項**：手冊第 6.4 節說管理隱性成本的第一步是「讓它現形」。
> 系統的價值不在於自動幫你省錢，而在於**把 1,200 萬的隱性成本從看不見變成看得見**。

## 6. 範圍邊界

### 6.1 這個系統做什麼

| 模組 | 做的事 | 階段 |
|---|---|---|
| 平台基礎 | 帳號、角色權限、部門、稽核軌跡、通知、附件 | P1 |
| 專案管理 | 專案主線、合約資訊、請款里程碑、變更追加單 | P1 |
| 進度追蹤 | 構件批次線（鋼構）／工項線（土建）、階段看板、異動歷程 | P1 |
| 請款收款 | 里程碑請款、應收、應付、現金流預測、專案損益 | P2 |
| 採購供應商 | 請購→詢比議→採購單→收料、供應商五維度評分 | P2 |
| **資產與庫存** | **公司所有東西的總覽**：建材（含型號尺寸材質）、零件耗材、工具、設備；物理位置、狀態、專案歸屬、出入庫、餘料、呆滯料 → 詳見 `開發/06_資產與庫存.md` | **P1（清冊）／P2（流程）** |
| 成本 KPI | 18 項 KPI 儀表板、六階段成本地圖、標準／實際差異分析 | P2+ |
| 生產製造 | 工單、途程、派工、報工、設備 OEE、換線紀錄 | P3 |
| 品質管理 | IQC／IPQC／OQC、不良重工報廢、PAF 品質成本 | P3 |
| 出貨交付 | 出貨單、裝載率、OTD 準時率、簽收 | P3 |
| 人力薪資 | 派工排班、出勤請假加班、證照到期、台灣薪資計算 | P4 |
| 行政簽核 | 通用表單簽核引擎、核決權限表 | P4 |
| SOP 知識庫 | 情境 SOP 文件、版本控管、掛勾流程節點 | P4 |

### 6.2 這個系統**不做**什麼

| 不做 | 理由 | 替代方案 |
|---|---|---|
| **正式會計帳務**（總帳、傳票、財報） | 已確認採「管理會計為主」 | 繼續用現有會計軟體／會計師，本系統提供 CSV／Excel 匯出對接 |
| **稅務申報**（401、扣繳憑單） | 同上 | 同上 |
| **CAD／BIM 繪圖** | 專業領域，不重造輪子 | 系統只存圖紙連結與版本紀錄 |
| **客戶對外入口** | 純內部系統 | 需要時另議 |
| **手機原生 App** | 已確認做響應式網站 | 手機瀏覽器即可，可加到主畫面 |
| **即時推播通知**（P1） | 8GB 機器不養常駐服務 | 站內通知 ＋ 每日排程掃描；真的需要即時再加 |
| **自動排程演算法**（自動排產） | 鋼構 job-shop 變數太多，先讓人排 | 系統提供資訊輔助人工決策 |
| **多公司／多租戶** | 只有一家公司用 | — |

### 6.3 灰色地帶：與現有會計軟體的分工

這條線要畫清楚，否則會出現兩套帳：

```
┌─────────────────────────────┐        ┌──────────────────────┐
│  本系統（管理會計）          │        │  現有會計軟體（財務會計）│
│                             │        │                      │
│  · 專案成本歸集             │  匯出   │  · 總帳／傳票          │
│  · 完全成本核算             │ ─────> │  · 進銷項發票          │
│  · 請款里程碑／應收追蹤      │  CSV   │  · 401 申報           │
│  · 應付款追蹤               │        │  · 財務報表            │
│  · 現金流預測               │        │  · 稅務               │
│  · KPI 與成本差異分析        │        │                      │
└─────────────────────────────┘        └──────────────────────┘
       給「管理決策」用                        給「對外申報」用
```

**判斷準則**：
- 「這個數字是給老闆做決策的」→ 本系統
- 「這個數字是要報給國稅局或給會計師簽證的」→ 會計軟體

**唯一的資料流方向**：本系統 → 匯出 → 會計軟體。不做雙向同步（避免對帳地獄）。

## 7. 三條不可妥協的設計約束

這三條凌駕於功能需求——**功能可以砍，這三條不能破**。

### 7.1 輕量：正式機只有 8GB RAM

- 目標常駐用量 **≤ 1.5GB**，平常只跑 3 個服務（nginx／Django／PostgreSQL）約 1.1GB
- 正式環境**沒有任何 Node 程序**——前端在建置期就編譯成靜態檔
- 明確不用：Elasticsearch、Kafka、Redis、Kubernetes、微服務、SSR
- 詳見 `開發/03_架構與部署.md`

### 7.2 響應式網站，手機優先

- 純網頁，手機／平板／桌機同一份程式
- **現場人員（約占使用者一半）用手機是主要輸入來源**，必須好用
- 報表類畫面只在桌機出現
- 詳見 `開發/04_UI設計原則.md`

### 7.3 第一性原理：UI 只留必要的

> **核心問句：這個元素移除後，使用者還能完成工作嗎？能，就移除。**

- 一個畫面回答一個問題
- 導航 ≤ 6 個主分頁
- 一頁 ≤ 7 個資訊區塊
- 明確不做：多層麵包屑、可自訂儀表板、主題切換、動畫特效、裝飾性圖表
- 詳見 `開發/04_UI設計原則.md`

## 8. 名詞定義

建立共同語言，避免文件與程式各說各話。

| 名詞 | 定義 | 英文／欄位 |
|---|---|---|
| **專案** | 一個承攬案，有合約、客戶、金額、工期 | Project |
| **專案類型** | 土建／鋼構／混合 | `project_type` |
| **主線階段** | 專案本身走的 7 個階段：接案→深化設計→報價→採購備料→施工中→完工驗收→結案 | Project Stage |
| **期別／標段** | 專案下的分期（如「第一期」），可有可無 | ProjectPhase |
| **追蹤單元** | 進度追蹤的最小單位。鋼構叫「構件批次」，土建叫「工項」 | TrackingUnit |
| **構件批次** | 一批同型構件（如「第一期-1F 鋼柱 80 支」），走 8 個廠內階段 | unit_type=`batch` |
| **工項** | 土建的一個施工項目（如「B1 結構體」），有分包商與完成百分比 | unit_type=`work_item` |
| **階段模板** | 一條可設定的流程（有哪些階段、什麼順序） | StageTemplate |
| **請款里程碑** | 合約約定的一次請款（如「第一期請款 30%」），有觸發條件 | BillingMilestone |
| **廠商** | 統稱，用類型區分：供應商／分包商／外包加工廠／運輸行 | Vendor |
| **真實時薪** | 月薪×13.5÷有效工時(1600)×(1+附加率)，約為表面時薪的 1.7–1.9 倍 | 手冊附錄 B |
| **完全成本** | 直接材料＋直接人工＋製造費用分攤＋交付成本＋管銷分攤 | 手冊 13.1 |
| **OEE** | 設備總效率 = 可用率 × 效能 × 良率 | 手冊 10.4 |
| **隱性成本** | 不出現在費用科目、但真實發生的成本（如庫存資金占用） | 手冊第 6 章 |
