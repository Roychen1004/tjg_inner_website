## 1. 核心問句

> **這個元素移除後，使用者還能完成工作嗎？能，就移除。**

這份文件的每一條規定，都可以回推到這一句。

### 1.1 三條硬規則

| # | 規則 | 檢驗方式 |
|---|---|---|
| 1 | **輕量** — 不引入重型前端函式庫 | 初始 JS gzip 後 < 200KB |
| 2 | **響應式，手機優先** — 現場人員是主要輸入來源 | 375／768／1440px 三個寬度無橫向捲軸 |
| 3 | **只留必要的** — 移除後仍能完成工作的就移除 | 實際畫面數 = 7，多出的要說明理由 |

## 2. 畫面盤點（P1 只做 7 個）

**每個畫面只回答一個問題。答不出「這個畫面回答什麼問題」的，就不該存在。**

| # | 畫面 | 回答的問題 | 主要使用者 | 裝置 | 導航 |
|---|---|---|---|---|---|
| S1 | 登入 | — | 全體 | 📱💻 | 無 |
| S2 | **營運總覽** | 「公司現在整體狀況如何？」 | 經營者、專案負責人 | 💻（📱簡化） | 分頁 1 |
| S3 | **專案** | 「這個案子進行到哪？」 | 專案負責人、廠長 | 📱💻 | 分頁 2 |
| S4 | **追蹤看板** | 「東西現在卡在哪一站？」 | 廠長、工地主任 | 💻（📱橫捲） | 分頁 3 |
| S5 | **請款收款** | 「錢收得回來嗎？」 | 會計、經營者 | 💻 | 分頁 4 |
| S6 | **產線** | 「機台在忙什麼？」 | 廠長 | 💻 | 分頁 5 |
| S7 | **我的工作** | 「我今天該做什麼？」 | 現場人員、工地主任 | **📱** | worker 首頁 |
| **S8** | **資產總覽** | 「**公司有什麼東西、在哪、什麼狀態、用在哪案？**」 | 倉管、廠長、採購、經營者 | 💻（📱查料） | **分頁 6** |
| — | 主檔設定 | — | 管理員 | 💻 | **Django Admin** |

**導航 = 6 個分頁**（**已達上限，之後要再加分頁必須先移除一個**）。
`worker` 角色只看到 S7，其餘分頁不顯示。

> 📌 S8 是依需求新增的第 8 個畫面，線框與規格見 `09_資產與庫存管理.md` §9。
> 它通過「一個畫面回答一個問題」的檢驗——回答的是「公司有什麼東西」，
> 這是其他七個畫面都答不了的問題。

### 2.1 為什麼主檔維護不做前端畫面

客戶、廠商、部門、使用者、階段模板——這些是**低頻、由單一角色操作**的維護作業。
Django Admin 已經提供列表、搜尋、篩選、排序、批次操作、稽核歷史，全部免費。

自己寫這些畫面要花 2–3 週，換來的只是「介面比較統一」。
**這筆交易不划算。** 管理員一個月開 Admin 兩次，統不統一不影響任何人的工作效率。

## 4. 色彩系統（已用程式驗證，非目測）

> ⚠️ **重要更正**：POC 現用的「8 個階段 8 種顏色」配色**沒有通過色盲安全驗證**。
> 以下是實測結果與修正方案。

### 4.1 POC 現用配色的驗證結果

用 OKLab ΔE ＋ Machado-Oliveira-Fernandes 色盲模擬實測 POC 的 8 色階段配色：

```
=== POC 鋼構批次 8 階段配色 (light, surface #ffffff) : 8 slots ===
  [PASS] Lightness band       all 8 inside L 0.43-0.77
  [FAIL] Chroma floor         #64748b (收尾) C=0.041 — 低於 0.10，讀起來是灰的
  [FAIL] CVD separation       #22c55e(安裝) ↔ #10b981(出貨進場) ΔE 5.9 — 低於 6.0 底線
  [FAIL] Normal-vision floor  #22c55e(安裝) ↔ #10b981(出貨進場) ΔE 6.3 — 遠低於 15 底線
  [WARN] Contrast vs surface  5 色低於 3:1
  -> FAILED
```

**最糟的四組配對**

| 配對 | 正常視覺 ΔE | 色盲 ΔE | 判定 |
|---|---:|---:|---|
| 加工 `#f59e0b` ↔ 表面處理 `#ef8c0b` | 4.4 | 3.9 | 🔴 **幾乎同色** |
| 出貨進場 `#10b981` ↔ 安裝 `#22c55e` | 6.3 | 5.9 | 🔴 **兩個綠分不出來** |
| 置料區 `#0d9488` ↔ 收尾 `#64748b` | 11.0 | 5.3 | 🔴 失敗 |
| 加工 `#f59e0b` ↔ 安裝 `#22c55e` | 23.4 | 5.7 | 🔴 色盲者看來相同 |

**還有一個更根本的問題**：POC 的階段色**撞到了狀態燈號**——
階段綠 `#10b981` 與「正常」綠 `#059669`、階段橘 `#f59e0b` 與「注意」黃 `#d97706` 幾乎同色。
使用者無法分辨「這個綠是指這一站，還是指狀態沒問題」。

### 4.2 修正方案：色彩分工

**根本原因是把兩件事都交給顏色。拆開就好：**

| 資訊 | 用什麼編碼 | 理由 |
|---|---|---|
| **在哪一站** | **欄位位置 ＋ 階段名稱** | 看板由左至右已經表達順序，顏色不增加任何資訊 |
| **走到哪個大階段** | **3 段序數藍色階**（淺→深） | 表達「離完成多遠」，深淺本身就有方向性 |
| **狀態好不好** | **狀態色 ＋ 圓點 ＋ 文字** | 這是唯一真正需要顏色的資訊 |
| **階段的特殊語意** | **圖示**（💰🚚⏸） | 顏色已經用完了，且圖示更明確 |
| **完成進度** | **單色進度條**（藍） | 量值編碼＝單一色相 |

### 4.3 階段序數色階（3 段，已驗證通過）

八個階段依性質分三組，每組一個色階：

| 組 | 涵蓋階段 | 色票 | OKLCH L |
|---|---|---|---|
| 廠內製造 | 進料驗收、加工、品檢 | `#86b6ef` | 0.764 |
| 中繼／外包 | 置料區、表面處理 | `#2a78d6` | 0.575 |
| 交付安裝 | 出貨進場、安裝、收尾 | `#104281` | 0.385 |

```
=== 3 段序數藍色階 ===
  [PASS] Lightness monotone   L=[0.764, 0.575, 0.385]
  [PASS] Adjacent ΔL          gaps=[0.189, 0.190]  (底線 0.06)
  [PASS] Light-end contrast   #86b6ef at 2.11:1     (底線 2.0)
  [PASS] Single hue           spread 3°             (上限 40°)
  -> ALL CHECKS PASS
```

> 💡 **為什麼是 3 段而不是 8 段**：驗證過的藍色階在淺色背景下，
> 相鄰步階要拉開 ΔL ≥ 0.06 才看得出差別，這條色階最多只能切出 **5 個**可辨識的階。
> 硬切 8 段的結果就是相鄰兩階看起來一樣——那還不如不上色。
> 三組分法同時對應真實的作業流程轉換（廠內 → 外包 → 現場），有意義而非湊數。

### 4.4 狀態燈號（保留色，絕不挪作他用）

| 狀態 | 色票 | 對白底對比 | 顯示方式 |
|---|---|---:|---|
| 正常 | `#059669` | 3.77:1 | ● 正常 |
| 注意 | `#d97706` | 3.19:1 | ● 注意 |
| **延誤** | **`#b91c1c`** | 4.83:1 | ● 延誤 |

> ⚠️ **延誤色由 POC 的 `#dc2626` 改為 `#b91c1c`**：
> 原色與「注意」的正常視覺 ΔE 只有 **14.4**（低於 15 底線）；改深後提升到 **18.8**，通過。

**實測區辨度**

| 配對 | 正常視覺 ΔE | 色盲 ΔE |
|---|---:|---:|
| 正常 ↔ 注意 | 23.7 | **7.9** ⚠️ |
| 正常 ↔ 延誤 | 32.0 | 8.6 ✓ |
| 注意 ↔ 延誤 | 18.8 | 8.8 ✓ |

> ⚠️ 「正常↔注意」的色盲 ΔE 為 **7.9**，落在 6–8 的警戒帶。
> **這個帶區只有在有次要編碼時才合法**——本系統一律用「**圓點 ＋ 中文字**」呈現狀態，
> **顏色永遠不是唯一的線索**。這也是狀態色的通則：不靠色相單獨傳達意義。

**與階段藍的區隔**（確認不會混淆）

| 配對 | 正常視覺 ΔE | 色盲 ΔE |
|---|---:|---:|
| 正常 ↔ 階段藍 | 21.2 | 20.1 ✓ |
| 注意 ↔ 階段藍 | 32.9 | 27.0 ✓ |
| 延誤 ↔ 階段藍 | 34.5 | 26.4 ✓ |

### 4.5 請款狀態

請款是**有序的四個狀態**，同樣用序數處理 ＋ 文字標籤：

| 狀態 | 文字 | 色票 | 底色 |
|---|---|---|---|
| pending | 未到 | `#64748b`（中性灰） | `#f1f5f9` |
| claimable | **可請款** | `#d97706`（需行動） | `#fffbeb` |
| invoiced | 已請款 | `#2a78d6` | `#eff6ff` |
| received | 已收款 | `#059669` | `#ecfdf5` |

> 💡 「可請款」刻意用**注意色**——它不是壞事，但**需要有人去做**。

## 5. 響應式規範

### 5.1 斷點

| 斷點 | 寬度 | 版面 |
|---|---|---|
| `sm` 以下 | < 640px | **單欄**。KPI 卡片 2 欄，其餘全部堆疊 |
| `sm`–`lg` | 640–1024px | 雙欄。KPI 卡片 3 欄 |
| `lg` 以上 | > 1024px | 完整版面。KPI 卡片 5 欄，主次區塊 2:1 |

### 5.2 手機硬性要求

| 項目 | 規格 |
|---|---|
| 觸控目標 | **≥ 44 × 44 px**（Apple HIG 標準） |
| 主要操作按鈕高度 | ≥ 48px；「確認回報」滿版 56px |
| 表單欄位 | 單欄堆疊，`font-size ≥ 16px`（**低於 16px iOS 會自動縮放頁面**） |
| 數字輸入 | `inputmode="numeric"`，彈出數字鍵盤而非全鍵盤 |
| 橫向捲軸 | **頁面本身絕不橫捲**；看板等寬內容放在自己的 `overflow-x:auto` 容器內 |
| 首屏 | 4G 網路 < 2 秒 |

### 5.3 按裝置分流的內容

| 內容 | 手機 | 桌機 |
|---|---|---|
| 我的工作 | ✅ 主畫面 | ✅ |
| 回報進度、推進階段 | ✅ **優先最佳化** | ✅ |
| 專案清單 | ✅ 單欄卡片 | ✅ |
| 追蹤看板 | ⚠️ 橫向捲動 | ✅ |

> 💡 **報表不上手機**不是偷懶，是誠實。在 375px 上看多欄表格是折磨，
> 給一句「請用電腦檢視」比給一個難用的畫面好。

| `ConfirmDialog` | 確認對話框 | 危險操作用紅色主按鈕 |
| `QuickIncrement` | 快速增量 | `+1/+5/+10`，級距由後端提供 |
| `EmptyState` | 空狀態 | **一句話，不畫空表格** |
| `Toast` | 操作結果提示 | 顯示 `side_effects`，如「已觸發第一期請款」 |

**shadcn/ui 提供的基礎元件**（Button／Input／Select／Dialog／Popover／Toast）**複製原始碼進專案**，
不是套件依賴——可以完全掌控，也不會因為套件升級而改變外觀。

---

## 7. 互動規範

| 情境 | 規範 |
|---|---|
| 操作回饋 | 所有寫入操作 **1 秒內**要有視覺回饋（成功 Toast 或錯誤訊息） |
| 錯誤訊息 | **講人話**：「已完成數量不可超過總數量（80）」，不是「validation error」 |
| 危險操作 | 刪除、回退、結案一律二次確認；確認鈕用紅色 |
| 載入中 | 骨架屏（skeleton），不用轉圈圈 |
| 表單驗證 | 失焦即驗證，不等到送出才報錯 |
| 樂觀更新 | 推進階段立即更新畫面，失敗再回捲並提示 |
| 空狀態 | 一句話說明 ＋ 一個主要動作，**不畫空的表格框** |
| 分頁 | 一頁 20 筆；看板不分頁（單一階段極少超過 20 筆） |

---

## 8. 明確不做的清單

| 不做 | 理由 |
|---|---|
| 多層麵包屑 | 只有兩層深度，用「返回」就夠 |
| 可自訂儀表板 | 使用者會花時間調版面，而不是做事 |
| 主題切換器（深色模式） | 內部系統、白天使用；多一套配色就多一套要驗證的東西 |
| 複雜篩選面板 | P1 只給 2–3 個常用篩選；要更複雜的用 Django Admin |
| 動畫特效與轉場 | 只保留必要的狀態變化過渡（≤ 150ms） |
| 引導導覽（onboarding tour） | 7 個畫面不需要導覽，需要導覽表示畫面設計失敗 |
| 裝飾性圖表 | 每個圖表都要能回答一個具體問題 |
| 圓餅圖 | 人類比較角度的能力很差；一律用長條圖 |
| 雙 Y 軸圖表 | 最常見的圖表錯誤；兩個尺度＝兩張圖 |
| 全域搜尋 | P1 各畫面有自己的 `q` 搜尋就夠 |
| 匯出 PDF | P1 不做；需要就用瀏覽器列印 |

## 9. 驗收清單

```
□ 畫面數量 = 8（多出的要說明理由）
□ 導航分頁 = 6（已達上限）
□ 每個畫面的資訊區塊 ≤ 7
□ 375 / 768 / 1440px 三個寬度，頁面本身無橫向捲軸
□ 手機上所有可點擊元素 ≥ 44×44px
□ 手機表單欄位 font-size ≥ 16px（不觸發 iOS 自動縮放）
□ 狀態一律「圓點＋文字」，沒有任何地方只靠顏色傳達狀態
□ 階段色階與狀態色實測分離（ΔE ≥ 20）
□ 初始 JS gzip 後 < 200KB
□ 首屏渲染 < 2 秒（4G 手機）
□ 沒有引入 Chart.js／D3／ECharts
□ 所有空狀態都是一句話，沒有空表格框
□ 所有錯誤訊息都是中文完整句子
```
