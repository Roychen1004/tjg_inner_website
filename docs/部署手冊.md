# 部署手冊

新機器（Ubuntu 24.04 + Docker）從零到能用，約 15 分鐘。

## 1. 完整流程

```bash
# 裝 Docker（官方腳本）
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER && newgrp docker

# 取得程式碼
git clone <repo> /opt/tjg-inner && cd /opt/tjg-inner

# 設定環境變數
cp deploy/.env.sample deploy/.env
python3 -c "import secrets; print(secrets.token_urlsafe(50))"   # 產生 SECRET_KEY
vi deploy/.env   # 填：SECRET_KEY、四組密碼、DEBUG=false、ALLOWED_HOSTS 加主機 IP

# 建置並啟動（web ~20MB / api ~160MB / db ~70MB，遠低於 1.5GB 目標）
docker compose build && docker compose up -d

# 建表與主檔
docker compose exec api python manage.py migrate
docker compose exec api python manage.py seed_masters
docker compose exec api python manage.py seed_accounts
python3 shell/set_roster_passwords.py   # 套用 帳號密碼.md 的一人一組密碼（見下方註）

# 要試用再載示範資料（一個案子：固越企業總部）；清除用 --clear
docker compose exec api python manage.py seed_demo

# 排程（備份與資源監控）
crontab -e   # 貼上 deploy/crontab.sample，TJG 換成實際路徑
```

> `seed_accounts` 只吃**一組** `SEED_DEMO_PASSWORD`，表達不出 `帳號密碼.md`
> 的一人一組。`set_roster_passwords.py` 讀那份 markdown 再套用——名冊的
> 唯一事實來源就是那份文件。跳過這步的話，下一節的 `verify.py` 會在登入就失敗。

## 2. 驗收

```bash
docker compose ps                                  # 三個服務都 Up
curl -s http://localhost:30080/api/v0.1/health     # {"status":"ok",...}
python3 shell/verify.py                            # 全流程整合驗收
docker stats --no-stream                           # 記憶體合計 < 300MB
```

⚠️ 附件下載一定要**打過 nginx（:30080）**驗——它走 X-Accel-Redirect，
直連 api:8000 會拿到空回應。`verify.py` 包含這項。

## 3. 正式上線前必做

1. 把員工姓名從職稱改成真名（設定 → 員工；名冊與密碼見 `帳號密碼.md`）
2. 確認 `deploy/.env` 的 SECRET_KEY 是新產生的、DEBUG=false
3. 跑一次備份還原演練：`deploy/backup.sh` 後，把 dump 還原到測試庫確認可讀
4. 客戶與分包商的**帳期**填進系統（現金流的準確度靠它）

## 4. 開發模式（前後端都 hot reload）

`docker compose` 會自動載入 `docker-compose.override.yml`，也就是**平常
`docker compose up -d` 起來的就是開發模式**：

| | 怎麼做到的 | 改完檔案 |
|---|---|---|
| 後端 | 原始碼 bind mount 進容器 + `gunicorn --reload` | 存檔後約 1 秒 worker 自己重啟 |
| 前端 | 多一個 `web-dev` 服務跑 Vite dev server，nginx 的 `/` 反向代理過去 | 存檔後瀏覽器不重整就換掉（HMR） |

網址仍然是 **http://localhost:30080**——nginx 還站在最前面，所以 `/api`、
同源 cookie、附件下載的 X-Accel-Redirect 全都跟正式環境一樣，
不會出現「開發好好的、上線壞掉」。

```bash
docker compose up -d          # 開發模式（第一次要等 npm ci，約 1 分鐘）
make dev-logs                 # 只看前端 dev server 與後端的日誌
make web-deps                 # 改了 package.json 之後重跑 npm ci
```

宿主機**不需要安裝 Node**：依賴裝在 named volume `web_node_modules` 裡。
除錯用的直連埠是 `:30173`（繞過 nginx 看 Vite；HMR 請走 :30080，
因為 HMR 的 websocket 埠是寫死對著 30080 的）。

⚠️ **正式部署要明確排除 override**，否則會把宿主機的原始碼與一個 Node
程序掛進正式環境：

```bash
docker compose -f docker-compose.yml build && docker compose -f docker-compose.yml up -d
# 等同 make prod-build && make prod-up
```

## 5. 日常維運

```bash
docker compose logs api --tail 50        # 看後端日誌
docker compose restart api               # 改了 .env 後重啟
git pull && docker compose build && docker compose up -d   # 更新版本
docker compose exec api python manage.py migrate           # 更新後補跑
deploy/backup.sh                         # 手動備份（cron 每日 01:00 自動跑）
```

## 6. 出事了看這裡

| 症狀 | 原因與解法 |
|---|---|
| api 一直重啟 | `.env` 少填（看 `docker compose logs api`）。九成是 SECRET_KEY 或資料庫密碼 |
| 登入沒反應／403 | `ALLOWED_HOSTS`／`CSRF_TRUSTED_ORIGINS` 沒加這台的 IP |
| 改了程式沒生效 | 開發模式下前後端都會自動重載；沒反應先看 `make dev-logs`。正式模式（`-f docker-compose.yml`）程式包在映像檔裡，要 `build` 再 `up -d` |
| 前端改了畫面不動 | HMR 的 websocket 斷了。看 `docker compose logs web-dev`；確認是從 :30080 進來的，不是 :30173 |
| 前端 502 | `web-dev` 還在跑 `npm ci`（第一次約 1 分鐘），等一下重整 |
| Admin 沒有 CSS | api 容器啟動時會收集靜態檔，重啟一次 api |
| 要直接看資料庫 | `docker compose --profile tools up -d pgadmin` → `http://127.0.0.1:30050`（用完 stop，省 300MB） |
| 密碼鎖住（連錯 5 次） | `docker compose exec api python manage.py axes_reset` |
