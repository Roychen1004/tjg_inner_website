# 開發指南

架構、規範、UI 原則各取必要的部分。長版在 `../封存/`。

## 架構

```
nginx (:30080)  靜態檔 + 反向代理 + /protected-media/（internal，附件下載）
  └ api        Django 5 + DRF + gunicorn（3 workers）
  └ db         PostgreSQL 16
前端建置期打包成靜態檔——正式環境沒有任何 Node 程序
```

Django apps：`core`（帳號/附件/通知）、`masters`（客戶/廠商/流程目錄/階段模板）、
`projects`、`tracking`、`billing`（應收）、`payables`（應付+現金流）、`analytics`（儀表板）、
`affairs`（行政事項）、`payroll`（薪資，D57）。

```
薪資（D57，`payroll`）：
```
PayrollPolicy        法規參數——最低時薪、加班倍率、勞健保費率、福利金%。
                     ⚠️ 一個數字都不寫死在程式裡：法規每年調，烤進程式
                     等於每次修法都要重新部署。預設值＝115 年現行法規
InsuranceGrade       投保薪資分級表（11 級）。勞健保算的是「申報的投保薪資」，
                     不是當月實發額
Holiday              國定假日，只影響「應上班天數」的預設值
SalaryProfile        一人一張，掛 core.User——名冊不另建一份。
                     時薪留空＝跟著 policy 的最低時薪走（調基本工資只改一處）
PayrollPeriod        一個月一張。確認時把整組法規參數存進 policy_snapshot 凍結，
                     之後調費率不會回頭改動已確認的月份（鐵律 5）
  └ PayrollRecord    期×人。前半是輸入（出勤），後半是輸出（gross/deduction/net
                     ＋ detail：每一行的「標籤×算式×金額」）
        └ PayrollLine  規則以外的加扣項（獎金、借支）
```
計薪方式三選一（`SalaryProfile.pay_type`），差別**只在「應發總額怎麼來的」**：
時薪制＝工時×時薪＋加班；月薪制（薪資總額）＝填的月薪；
月薪制（實際領取）＝`solve_gross_from_net()` 反推——
福利金按總額 1% 算，所以不能把扣款直接加回去，要解
`總額 = (實領 + 固定扣項) ÷ (1 − 1%)`，最後還有迴圈補四捨五入的零頭
（打「實領 35,000」就必須剛好 35,000）。
月薪換時薪 `÷ monthly_wage_divisor`（法定 240），**要取到分**——
無限小數印在算式上等於沒有算式。

計算只有一條路徑：`payroll/services/calc_service.calculate()`——試算與存檔
共用，才不會「畫面試算是這個數、存下去變另一個數」。每一行都輸出算式字串
（`10 小時 × 196 × 1.34`），因為會計師是照算式驗算的，只給總額她不會信。

⚠️ **未滿一個月時，三種保險的規則不一樣**（`workday_service`，錯過一次就是錢）：

| | 規則 | 到職當月 | 離職當月 |
|---|---|---|---|
| 勞保、勞退 | 按日，**分母一律 30**（不分大小月） | 30 − 到職日 + 1 | 離職日 |
| 健保 | **不按日**，整月，由「當月最後一天」的投保單位負擔 | 照收 | 月中走＝不收 |

2 月最容易錯：2/2 到職做到 2/28 是 **29 天**（做到月底就算到第 30 天），
不是 28 − 2 + 1 = 27 天。

健保雇主負擔用**全國平均眷口數 0.56**，與員工實際眷屬數無關——
員工加保眷屬多出來的錢全是員工自己付。

⚠️ 薪資單的維護分兩層，界線是「**會不會蓋掉會計師手 key 的資料**」：

- `sync_records()`——**安全**：補建缺少的、更新勞保勞退天數與健保收不收、
  移除當月不在職者。掛在建立月份／改期間設定／改員工設定／同步名冊／
  重算薪資／確認前，**自動跑**，使用者不必按任何按鈕
- `reset-hours` 端點——**會覆蓋** `work_days / normal_hours / ot_weekday_1_hours`，
  所以是明確按下去的「重設工時」，前端還會先跳確認框。`?deep=true` 連手填的
  加班請假一起歸零

`sync_records(rebaseline_users=...)` 只允許**指定的人**重帶工時。
不能只看「算出來的天數跟記錄不一樣」就重帶——改期間的應上班天數也會讓天數
不一樣，那樣會洗掉 key 到一半的資料。改到職／離職日時才傳那個人自己。

政府公告的級距只放**官方頁面連結**（`payroll/reference.py`），不留 PDF 副本——
法規每年修，副本會變成「系統裡那份是舊的」。

薪資 Excel 在 `payroll/services/payroll_export.py`（`GET /payroll-periods/{id}/xlsx`），
三張表：薪資總表、計算明細、銀行匯款。★ 計算明細那張要留著**算式字串**，
不能只匯數字——匯出去也要能驗算，那是這個功能存在的理由。

國定假日走 `calendar_import`：政府資料開放平臺 dataset 14718，
一年一個 CSV，網址是每年不同的 uuid，所以要先打資料集 API 找當年度那筆。
**要連外網**，正式機可能連不出去——所以是手動按的，不是排程。

⚠️ `SalaryProfile` 存檔時會自動把到職／離職日套進**所有草稿月份**
（`apply_profile_to_drafts`）。使用者不會記得要再去按「產生薪資單」，
所以不能要求他多按一步。已確認／已發放的月份不動。

權限（D40，矩陣在 main/utils/permissions.py）：經理＋superuser 改一切；
會計師只改金流（edit_milestone/edit_payable/pay_payable…，approve_payable 仍限經理）；
員工全唯讀（金額拿不到），僅 can_operate 自己被指派的單元；
設定頁人人可看（NAV settings=None），寫入靠 manage_masters 擋。
帳號名冊 15 人與密碼在 docs/帳號密碼.md（老闆要求明文）。

遺留欄位：main_template/main_stage 還在 DB（NOT NULL；migrations 只加不改，
建案時仍寫入預設值），但 API 不再輸出、advance-stage 端點已移除（D39）——
主線由前端從 flow_units 自動判定，結案走「編輯專案」改 lifecycle。

甘特：專案卡片迷你甘特（五階段 bar＋日期網格）、看板日曆甘特（D40：滾輪
縮放 7 天～1 年、拖曳平移，表頭密度隨 px/天 自動調）、

```

附件檔案存哪：named volume `media` → 容器內 `/app/media`（MEDIA_ROOT），
路徑 `attachments/YYYY/MM/<uuid>.<副檔名>`——刻意不用原始檔名（亂碼、
覆蓋、路徑注入），原始檔名存欄位、下載時還原。下載走 Django 驗權限後
X-Accel-Redirect 給 nginx 的 internal `/protected-media/`。

## 鐵律（違反過、修過、不要再犯）

1. **金額用 Decimal**；「沒填」與「填 0」是兩件事——判斷用 `"field" not in attrs`，不用 `if not value`
2. **權限檢查在業務規則之前**——先 403 再 400，否則等於告訴無權限的人「補個欄位就能過」
3. **DB CHECK 是最後防線不是錯誤訊息**——view 層先驗，給人看得懂的中文
4. 列表一律 `select_related/prefetch_related`；兩個 Sum 走不同關聯要用 Subquery，
   不然 JOIN 列數相乘、金額安靜地變大
5. 錢的狀態機：往前一次一步、往回必填原因、寫入不可竄改的 Log 表
6. 附件：magic bytes 驗檔、照片先 `exif_transpose` 再剝 EXIF、
   下載走 X-Accel-Redirect（nginx 要自己再設一次 nosniff——它不轉發上游自訂標頭）
7. 金額型附件（合約/發票）跟著 `view_money` 權限走，清單也不出現
8. 範圍外資料回 404 不回 403
9. 錯誤訊息說「怎麼辦」，不只說「不行」
10. **法規數字不寫死**（D57）——費率、倍率、級距一律做成可編輯的資料，
    不是程式常數。修法時要能在畫面上改完就生效，不必重新部署

## API 慣例

- Session + CSRF（同網域），路徑 `/api/v0.1/...` 結尾不加斜線
- 狀態轉換用具名 action（`POST .../transition`），不用 PATCH 欄位
- `next_states` 由後端算好回給前端——狀態機只有一份
- 型別鏈：`manage.py spectacular --file openapi.yaml` → `npm run types` → `schema.d.ts`。
  改了 API 一定重跑，不手抄型別

## UI 原則

- 六個分頁，一個畫面回答一個問題；分頁由後端 `visible_nav` 決定
- 元素的存在要通過「砍掉它，有人會做不了事嗎」
- 顏色永遠伴隨文字標籤；金額欄位無權限時是 null（不是 0）
- 手機優先：路由 lazy 載入、首屏 gzip 預算 200KB（現況約 68KB + 頁面塊）
- 共用格式函式放 `web/src/lib/`，不從頁面 import——會把整頁拉進別人的 chunk

## 開發環境（前後端都 hot reload）

`docker compose up -d` 會自動載入 `docker-compose.override.yml`，起來的就是
開發模式——**改檔案存檔就生效，不用 build**：

```
瀏覽器 → nginx(:30080) ─┬─ /            → web-dev(Vite dev server)  改 .tsx → HMR
                        ├─ /api/        → api(gunicorn --reload)    改 .py  → 約 1 秒重啟
                        └─ /protected-media/  附件（X-Accel-Redirect，跟正式環境一樣）
```

刻意讓 nginx 留在最前面而不是直接開 :5173：這樣開發網址跟正式環境同一個
形狀（同源 cookie、`/api` 路徑、附件走 X-Accel-Redirect），少一整類
「開發好好的、上線壞掉」。宿主機不必裝 Node——依賴在 named volume 裡。

| 情況 | 指令 |
|---|---|
| 看前後端日誌 | `make dev-logs` |
| 改了 `package.json` | `make web-deps`（重跑 npm ci） |
| 改了 `deploy/.env` | `docker compose restart api` |
| 加了 migration | `docker compose exec api python manage.py migrate`（或重啟 api，AUTO_MIGRATE 會跑） |
| 前端 502 | `web-dev` 還在跑 npm ci，等一下 |
| 改前端畫面不動 | HMR websocket 掛了；確認網址是 :30080（HMR 的埠寫死對著它） |
| `web/dist` 變成 root 擁有、刪不掉 | 在 `web-dev` 容器裡跑過 `npm run build`——那個容器是 root。要正式建置請用 `make prod-build`（在映像裡建，不碰宿主機）；要清掉已產生的：`docker compose exec web-dev rm -rf /app/dist` |

⚠️ **正式部署要明確排除 override**：`make prod-build && make prod-up`
（＝`docker compose -f docker-compose.yml ...`）。正式模式下程式碼包在映像裡，
改了要重 build；映像中也不存在任何 Node 程序。

migrations 一律**只加不改**（系統已有資料）。
