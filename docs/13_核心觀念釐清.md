# 13 — 核心觀念釐清

> 鐵正綱工程 內部管理系統
> 2026-08-02｜回答實際使用後提出的疑問

這份文件回答幾個問題。它們看起來是「操作問題」，其實都是**模型設計問題**——
搞錯了，做出來的東西就會答非所問。

## 1. 階段和完成度是什麼關係？

### 1.1 先講結論

| | 回答的問題 | 例子 |
|---|---|---|
| **階段** | 這批東西**走到哪一站**了 | 第 3 站「品檢」（共 9 站） |
| **完成度** | **目前這一站**做了多少 | 這一站 20 / 24 支 |

**完成度不是整批從頭到尾的累計進度。** 它是「這一站的進度」，換站會歸零重算。

### 1.2 為什麼是這樣

拿「第一期-1F鋼柱，24 支」走一次：

```
進料驗收   24 支料到齊、驗收完 24 支  → 100% → 推進
   ↓ 完成度歸零
加工       今天加工 5 支、明天 8 支…做完 24 支 → 100% → 推進
   ↓ 完成度歸零
品檢       檢查 24 支，全部合格 → 100% → 推進
   ↓ 完成度歸零
置料區     堆著等出貨（這一站沒有「做幾支」，直接推進）
   ↓
表面處理   送外包鍍鋅，回廠 24 支 → 100% → 推進
   ↓
出貨進場   分兩車運到工地，24 支到齊 → 100% → 推進
   ↓
進場簽收   業主簽收 ← ★ 這一站觸發請款
   ↓
安裝       吊裝 24 支
   ↓
收尾       補漆、清運
```

**每一站都要對這 24 支做一次事。** 「加工做完 24 支」不代表「品檢也檢完 24 支」——
那是兩件不同的工作，各自要從 0 數到 24。

所以：
- 現場師傅回報「今天做了 5 支」＝ **這一站**做了 5 支
- 推進到下一站時，完成度歸零，重新數
- 舊的數字寫進**階段歷程**，「加工那一站到底做了幾支」永遠查得回來

### 1.3 這是一個已修正的錯誤

⚠️ **2026-08-02 之前的版本，完成度是跨階段累計的**，結果是：

```
加工      24/24 = 100%  → 推進
品檢      24/24 = 100%  ← 一進站就 100%，但根本還沒開始檢
```

第二站起，完成度這個欄位就等於作廢了。已修正（決策 D22）。

### 1.4 整體進度看哪裡？

看**階段軌道**，不是看完成度。

```
①──②──③──④──⑤──⑥──⑦──⑧──⑨
       ▲
    第 3 站 / 共 9 站
```

如果你需要一個「整體百分比」，正確的算法是
`(已完成站數 + 這一站的完成度) ÷ 總站數`——但我們**刻意不顯示這個數字**。

原因：九站的工作量差很多。「加工」可能花兩週，「置料區」是放著不動。
把它們當等權重平均，會得到一個看起來精確、實際上騙人的數字。
**與其給一個假的整體進度，不如誠實顯示「在第 3 站，這一站做了 8 成」。**

## 2. 一個專案應該有幾個追蹤單元？

### 2.1 你的理解需要修正

> 「每個專案都應該至少有兩個追蹤單元：
>  一個是構件批次（材料的準備），一個是土建工項（蓋房的進展）」

這裡有兩個誤解：

**誤解一：構件批次 ≠ 材料準備**

構件批次涵蓋鋼構的**整個承攬範圍**，包含工地安裝：

```
進料驗收 → 加工 → 品檢 → 置料區 → 表面處理 → 出貨進場 → 進場簽收 → 安裝 → 收尾
└────── 廠內 ──────┘              └────────── 工地 ──────────┘
```

後面四站都在工地。所以構件批次**不是**「準備材料」，而是「這批鋼構從進料到裝完的全程」。

**誤解二：兩者不是同一棟樓的兩個面向，是兩種不同的承攬範圍**

```
土建工項  = 我們承攬的【土建工程】部分   基礎、結構體、泥作、粉刷…
構件批次  = 我們承攬的【鋼構工程】部分   進料、加工、鍍鋅、運送、吊裝…
```

一個案子有沒有這兩者，取決於**合約簽了什麼**：

| 案子類型 | 構件批次 | 土建工項 | 例子 |
|---|:--:|:--:|---|
| 純鋼構代工 | ✔ | ✘ | 固越案——業主自己找土建包商，我們只做鋼構 |
| 純土建 | ✘ | ✔ | 只承攬基礎與RC結構 |
| 統包／混合 | ✔ | ✔ | 我們同時做土建與鋼構 |

**固越案在系統裡就只有構件批次，沒有土建工項——這是對的，不是漏建。**

### 2.2 實際上會有幾個？

**遠不止兩個。** 一個案子通常有十幾到數十個追蹤單元。

拆分的原則是：**一起走完整條流程的一組東西，算一個追蹤單元。**

固越案目前的拆法：

```
第一期
  ├─ 第一期-1F鋼柱      31.68 噸
  ├─ 第一期-桁架A區       9.60 噸
  ├─ 第一期-樓板鋼樑     26.28 噸
  └─ 第一期-樓梯鋼構      8.40 噸
第二期
  ├─ 第二期-2F鋼柱      25.34 噸
  ├─ 第二期-樓板鋼樑     19.71 噸
  └─ 第二期-樓梯鋼構      6.72 噸
```

為什麼這樣拆而不是「一個案子一批」：

| 理由 | 說明 |
|---|---|
| **分批出貨** | 1F 鋼柱先做好先送，不用等樓梯 |
| **分批請款** | 合約按期別請款，期別要對得起來 |
| **看得出卡在哪** | 全部混成一批，就只知道「這個案子在加工」，不知道是哪一部分卡住 |
| **分開指派** | 不同批可以派給不同的人 |

反過來，拆太細也不好：「1F-A1 柱」「1F-A2 柱」各建一筆，
會變成幾百張卡片，看板就沒法看了。

**判準：這一組東西會不會一起走、一起出貨、一起請款？會，就是一個追蹤單元。**

### 2.3 土建工項怎麼拆

按 **WBS（工作分解結構）** 拆，而不是按數量：

```
├─ A區基礎工程       放樣定位 → 施工中 → 自主檢查 → 監造查驗 → 完成
├─ B區基礎工程
├─ 1F 結構體
├─ 2F 結構體
└─ 外牆粉刷
```

土建用**百分比**而不是數量，因為「基礎工程做了幾支」問不出來，
只能問「做了幾成」——而這個成數由**監造查驗通過**認定（決策 D14），
不是自己說了算。

## 3. 資產該放什麼？需不需要另做一套倉儲系統？

### 3.1 不需要另做一套。這個就是。

現在的資產模組已經是一套倉儲系統的核心：位置階層、批號、出入庫異動、
材質證明追溯、庫齡分級。**缺的不是系統，是採購流程那一段**（P2 才做）。

再做一套的話，會出現兩份庫存數字，然後永遠對不起來。

### 3.2 但要分清楚兩種東西

這是第一性原理的分法：**問的問題不同，就該分開管。**

| | 工具／設備 | 建材／零件耗材 |
|---|---|---|
| **問的問題** | 「這一台**在誰手上**？」 | 「這個規格**還剩多少**？」 |
| **管理單位** | 一台一台（個體） | 一批一批（數量） |
| **識別方式** | 財產編號 TL-0031 | 批號 HB-SN490-300-202608-001 |
| **關鍵欄位** | 持有人、位置、校驗到期日 | 數量、規格尺寸、爐號、庫齡 |
| **資料表** | `AssetUnit` | `Lot` |
| **前端頁籤** | 工具設備 | 建材零件 |

硬塞進同一張表會怎樣：一支扭力扳手要填「數量 1」，
一批 300 支 H 型鋼要填「財產編號」——兩邊都彆扭，兩邊都沒答好問題。

### 3.3 什麼該放進來

**該放：**

| 類型 | 例子 | 為什麼 |
|---|---|---|
| 設備 | 雷射切割機、CNC、天車、電焊機 | 要知道在哪、誰在用、什麼時候保養 |
| 工具 | 扭力扳手、量具、吊帶吊具、發電機 | **校驗到期會影響驗收**，一定要追 |
| 建材 | H型鋼、鋼板、角鋼、螺栓 | 要知道還剩多少、規格對不對、材證在不在 |
| 零件耗材 | 焊條、砂輪片、防鏽漆 | 有安全存量的才值得管 |

**不該放：**

| 類型 | 為什麼不放 |
|---|---|
| 辦公文具、清潔用品 | 管理成本大於價值。買了就用，不用追蹤 |
| 一次性低值耗材 | 手套、口罩。列進去只會讓清單變雜訊 |
| 車輛 | 有里程、油耗、保險、駕駛——那是另一套領域模型，硬塞進來會兩邊都做不好。**P3 再說** |
| 不動產 | 這是財務科目，不是現場管理對象 |

**判準：這個東西找不到／壞了／過期了，會影響工程進度或驗收嗎？會，就放進來。**

### 3.4 建材為什麼不能直接改數字

系統**刻意不提供**「修改庫存數量」這個功能。要改只有三條路：

```
入庫（+）    盤點調整（±，必須填原因）    領用出庫（−）
```

每一筆都寫一條不可竄改的異動紀錄。

理由：直接 UPDATE 數字是最容易做的，也是最容易在半年後變成
**「帳面 300 支、實際 180 支，沒人知道那 120 支去哪」**的做法。

盤點調整必須填原因也是同一個道理——帳實不符是管理問題，
讓人隨手改而不用交代，等於承認帳沒在管。

### 3.5 現在能做什麼、還缺什麼

| 功能 | 狀態 |
|---|---|
| 工具設備建檔、派用、歸還、送修、校驗提醒 | ✔ 前端可操作 |
| 建材入庫（期初盤點建檔）、盤點調整、領用出庫 | ✔ 前端可操作 |
| 出入庫歷程、材證與爐號追溯 | ✔ |
| 找料（規格、尺寸、餘料長度查詢） | ✔ |
| 庫齡分級與呆滯料警示 | ✔ 資料層已算，`scan_alerts` 排程 W8 接 |
| **請購 → 詢比議價 → 採購單 → 收料** | ☐ **P2** |
| 餘料切割拆批 | ☐ P2 |
| 條碼／QR 掃描 | ☐ P3（要先確定現場願意用手機掃） |

**品項主檔（規格、材質、尺寸、是否需材證）在 Django Admin 建**——
`/admin/masters/item/`。它欄位多（依料型不同，鋼板問厚寬長、H型鋼問腹板翼板），
Admin 的表單處理這種情況比自己刻一個好。

## 4. 期別（標段）是什麼？

**是工程的分期，不是分期付款**——雖然兩者常常對得起來。

```
固越企業總部案
├─ 第一期  ← 期別
│    ├─ 第一期-1F鋼柱      31.68 噸  ← 追蹤單元
│    ├─ 第一期-桁架A區       9.60 噸
│    ├─ 第一期-樓板鋼樑     26.28 噸
│    └─ 第一期-樓梯鋼構      8.40 噸
└─ 第二期
     ├─ 第二期-2F鋼柱      25.34 噸
     └─ …
```

它做兩件事：

1. **把追蹤單元分組**——第一期的批次歸第一期
2. **決定簽收時觸發哪一筆請款里程碑**

合約寫「第一期構件全數運抵並經業主簽收後請款 40%」時，
系統要知道「**哪些批次算第一期**」——靠的就是期別。
里程碑也可以綁期別，兩邊對上了，簽收才會觸發正確的那一筆。

### 4.1 沒有分期的專案怎麼辦

**一樣能運作。** 里程碑就以**全案**為範圍。

南投案就沒有分期——它的里程碑是「每批按量分批請」，不需要分組。

所以新增追蹤單元時看不到期別欄位，是因為那個專案還沒建期別，不是壞掉。
現在表單會直接說明並指路：

> 這個專案還沒有分期。若合約是分期請款（第一期／第二期…），
> 請到**專案頁展開該案 → 期別**建立，建好後這裡就會出現選項。

### 4.2 在哪裡建

**專案頁 → 展開該案 → 期別**。輸入名稱就好，順序自動遞增。

兩條保護規則：
- 底下還有追蹤單元的期別**不可刪除**（會提示還有幾個）
- 被請款里程碑引用的期別**不可刪除**（刪了簽收會找不到對應的請款條件）

## 5. 「合約里程碑」與「請款事件」差在哪？

### 5.1 一句話

> **里程碑是「合約寫的條件」，請款事件是「實際可以開的那筆錢」。**
>
> 里程碑是**計畫**，請款事件是**事實**。

### 5.2 三層結構

```
專案　固越企業總部案　合約 8,000 萬
│
├─ 期別（工程的分期）
│   ├─ 第一期 ─── 1F鋼柱、桁架A區、樓板鋼樑、樓梯鋼構
│   └─ 第二期 ─── 2F鋼柱、樓板鋼樑、樓梯鋼構
│                        │
│                        │ 業主簽收
│                        ↓
└─ 合約里程碑（你自己建，抄合約）
    ├─ 1. 簽約訂金        30%  手動
    ├─ 2. 第一期請款      30%  該期全部簽收 ←─ 綁「第一期」
    ├─ 3. 第二期請款      30%  累計重量達 80% ←─ 綁「第二期」
    └─ 4. 完工尾款        10%  手動
             │
             │ 條件達成，系統自動產生
             ↓
        請款事件（實際的錢）
          2,400 萬  可請款 → 已請款 → 已收款
```

### 5.3 兩者對照

| | 合約里程碑 | 請款事件 |
|---|---|---|
| **是什麼** | 合約上寫的每一條請款條件 | 實際可以開發票的那一筆錢 |
| **性質** | 計畫 | 事實 |
| **誰建的** | **你自己建**（簽約後抄合約） | **系統自動產生**（簽收觸發）；手動型由會計自己按 |
| **什麼時候** | 接到案子、簽完約就建 | 觸發條件達成的那一刻 |
| **幾筆** | 合約寫幾條就幾筆，通常 3～5 筆 | 看觸發方式，可能 1 筆也可能很多筆 |
| **有狀態嗎** | 有（彙總用）：未到／可請款／部分／已請款／已收款 | **有（實際操作）**：可請款 → 已請款 → 已收款 |
| **在哪一頁** | 請款收款 → 合約里程碑 | 請款收款 → 請款事件 |

**⚠️ 沒有里程碑，請款頁就永遠是空的。** 簽收再多批也不會有錢跑出來——
因為系統不知道「什麼情況算可以請款」。

### 5.4 為什麼要分兩層

因為合約寫「**按實際交貨數量分批請領**」時，**一條里程碑會產生好幾筆錢**：

```
分批交付計價　5,040 萬　每批按量分批請
  ├─ 桁架A區 42 噸 → 3,024 萬　已收款  ✔
  ├─ 桁架B區 28 噸 → 2,016 萬　已請款
  └─ 桁架C區 尚未簽收 ──────────  未產生
```

同一條合約條件，三批的狀態完全不同。硬塞在一層裡，
沒辦法同時表達「已收、已請、還沒到」——單一狀態機表達不了三種狀態並存。

四種觸發方式產生幾筆：

| 觸發方式 | 產生幾筆請款事件 | 什麼時候 |
|---|:--:|---|
| 手動 | 1 | 會計自己按「建立請款」 |
| 該期全部簽收 | 1（全額） | 最後一批簽收時 |
| 累計重量達門檻 | 1（全額） | 累計噸數 ≥ 門檻（如 80%） |
| **每批按量分批請** | **N** | **每批簽收各產生一筆**，金額按噸數佔比分攤 |

### 5.5 跟「期別」的關係

期別是**工程的分期**（第一期／第二期），不是分期付款——**但兩者常常對得起來**，
因為合約通常就是按工程分期來訂請款條件的。

三者的關係是：

```
追蹤單元 ──屬於──> 期別 <──綁定── 合約里程碑 ──產生──> 請款事件
```

某一批簽收時，系統做三件事：

1. 看這一批屬於**哪一期**
2. 找到**綁那一期的里程碑**
3. 評估該里程碑的觸發條件有沒有達成

所以「第一期請款」只會被第一期的批次觸發，第二期的批次簽收再多也不會動到它。

**沒有分期的專案，里程碑就以全案為範圍**，一樣能運作——
南投案就是這樣（它用「每批按量分批請」，不需要分組）。

系統畫面上會直接標出來：

```
第一期請款   該期全部簽收   只看 第一期
簽約訂金     手動          全案範圍
```

### 5.6 你該做什麼

| 順序 | 做什麼 | 在哪 |
|:--:|---|---|
| 1 | 簽完約，把合約每一條請款條件建成一筆里程碑 | 請款收款 → 合約里程碑 → 新增 |
| 2 | 如果合約是分期的，先建期別，再把里程碑綁上去 | 專案頁展開該案 → 期別 |
| 3 | 之後就不用管了。現場登錄簽收時系統自己判斷、自己通知會計 | — |
| 4 | 會計把請款事件從「可請款」推到「已請款」→「已收款」 | 請款收款 → 請款事件 |

第 3 步是整個系統的價值所在：**現場的一個動作直接變成財務上可以請的一筆錢，
中間沒有人要記得去通知會計。**

> 請款頁右上角有「這兩個差在哪？」按鈕，同樣的說明可以隨時打開來看。

## 6. 什麼可以自己改、什麼是寫死的

### 6.1 在前端「設定」分頁改（經營者與系統管理員）

| 項目 | 說明 |
|---|---|
| **客戶** | 每接一個新案就要建 |
| **廠商** | 供應商／分包商／外包加工／運輸行，可複選類型 |
| **員工與角色** | 到職、離職、換部門、調角色 |

新增員工時給預設密碼 `28494320`，**強制首次登入自行修改**。
忘記密碼用「重設密碼」按鈕，會留下系統紀錄。

⚠️ **員工不提供刪除**。離職請「停用」——他做過的推進、簽收、請款異動都掛在他名下，
刪了歷史就斷了。有案子的客戶、被引用過的廠商同理。

### 6.2 在 Django Admin 改（欄位多、動得少）

| 項目 | 路徑 |
|---|---|
| 物品主檔（規格、材質、尺寸） | `/admin/masters/item/` |
| 位置階層（倉庫／儲位／工地／外包廠） | `/admin/inventory/location/` |
| **階段流程**（幾站、叫什麼、哪一站觸發請款） | `/admin/masters/stagetemplate/` |
| 產線 | `/admin/production/productionline/` |
| 系統參數（時薪、費用率、庫齡門檻…） | `/admin/core/systemparameter/` |

判準：**動得頻繁、欄位少的搬前端；動得少、欄位多的留 Admin。**

物品主檔依料型有不同的尺寸欄位（鋼板問厚寬長、H型鋼問腹板翼板厚），
Admin 的表單處理這種情況比自己刻一個好。

### 6.3 寫死在程式碼裡的

| 項目 | 為什麼不開放 |
|---|---|
| 專案類型（土建／鋼構／混合） | 只有三種，且決定底下能建哪種追蹤單元。是結構性分類，不是設定值 |
| 進度算法（數量 vs 百分比） | 數學不同，不是設定問題 |
| 請款觸發方式（四種） | 每一種都有各自的判斷邏輯 |
| 狀態燈號（正常／注意／延誤） | 三種已足夠，多了反而看不出輕重 |

### 6.4 新增一種「追蹤單元類型」＝新增一條階段模板

在 Admin 建一條「鋼構－免表面處理（7 站）」，
它**立刻出現在前端的「階段流程」下拉裡**，不用改程式、不用重新部署。

模板底下的每一站可以設五個旗標：

| 旗標 | 意思 |
|---|---|
| 💰 `is_billing_trigger` | 進入這一站會評估請款觸發 |
| ✍ `requires_signoff` | 這一站要業主簽收 |
| 🚚 `is_outsource` | 這一站要填外包協力廠與進出廠日 |
| ⏸ `is_hold` | 等待狀態，不計入產能 |
| ⚙ `is_core` | 核心工序（P3 算 OEE 用） |

⚠️ **已經有階段異動紀錄的追蹤單元不准換模板**。
中途換軌會讓歷程對不上、請款觸發條件跟著錯。要換就建新的。
