# 第四輪｜2026-08-05　下一階段功能規劃

> 這三則是**動工前**的決策。規格見
> `開發/08_附件與預覽.md` 與 `開發/09_應付與現金流.md`。

## D30　附件要能預覽到什麼程度？

**問**：要能上傳合約、設計圖、流程圖、時程圖，並且讓使用者預覽。

**答**：**只預覽 PDF 與圖片，其餘明講要下載。**

**硬限制**：瀏覽器只能原生顯示 PDF 與圖片。

| 格式 | 能預覽 | 要預覽的話得裝什麼 |
|---|:--:|---|
| PDF、JPG、PNG | ✔ | 什麼都不用，瀏覽器內建 |
| XLSX（時程表） | ✘ | LibreOffice headless，**+500MB** |
| DWG（CAD 圖） | ✘ | CAD 轉檔引擎，更重且多半要付費授權 |

裝轉檔服務**直接撞破 8GB 的約束**（決策 D07）。不裝。

**為什麼這樣夠用**：合約、簽證、檢驗報告本來就是 PDF，現場照片是 JPG——
**九成以上的使用情境都能預覽**。要看 CAD 圖的人電腦裡本來就有 AutoCAD，
在瀏覽器看一張不能量測、不能比對圖層的縮圖對他沒有用。

**不做「假的預覽按鈕」**——按了跳「無法預覽」比一開始就說清楚更糟。

> 若日後想讓圖說一定看得到：作法是規定「上傳 DWG 時同時附一份簽核版 PDF」。
> 那是流程問題，不是技術問題。

**改的成本**：低（只是介面文案與判斷）。

---

## D31　應付款要管到多廣？ ⚠️

**問**：要能看到未來哪天要付多少錢、有哪些。

**答**：**只管關於工程案的大型花費。**

| 進系統 | 不進系統 |
|---|---|
| 材料採購、分包工程、外包加工、運輸 | 薪資、租金、水電、稅金、保險 |

**同時要在專案底下新增「跟包商合作的付費金額」**——也就是**分包合約**。
現在只有 `TrackingUnit.subcontract_amount` 一個孤立欄位，沒有合約、
沒有付款條件、沒有計價、沒有付款日，等於沒有。

### 代價要講清楚

**這是「專案現金流」不是「公司現金流」。** 少了每月固定支出，**預測會偏樂觀**。
畫面上會固定標註這一點，否則看的人會以為累計是正的就沒事。

好處是範圍明確、資料來源都在既有的工程流程裡，**不必等薪資模組（P4）就能用**。

### 設計原則：跟收款側對稱

```
應收  專案       → 合約里程碑 → 請款事件   可請款 → 已請款 → 已收款
應付  分包合約   →            → 應付款項   待計價 → 已核可 → 已付款
```

會計學會一邊就等於學會另一邊——狀態往前推、往回轉要填原因、
每一步留不可竄改的歷程，兩邊一模一樣。**少學一套東西。**

### ⚠️ 兩件會讓數字全錯的事，需要你確認

| 問題 | 為什麼致命 |
|---|---|
| **支票票期** | 台灣營造業大量用支票。開票日 ≠ 兌現日，中間可能還有 60–90 天。不算的話**現金流會早算兩三個月** |
| **含稅還是未稅** | 請款單開含稅、實際進出的錢也含稅，但合約通常談未稅。搞混就是 5% 的系統性誤差 |

這兩個沒對，整張表的日期跟金額都是錯的，**而且錯得很有說服力——比沒有這張表更危險**。

**改的成本**：高（新資料模型 ＋ 新畫面，約 11.5 個工作天）。

## D32　附件要掛在哪些東西上？

**答**：**專案 ＋ 追蹤單元 ＋ 請款事件。**

| 掛在 | 放什麼 | 頻率 |
|---|---|---|
| 專案 | 合約、施工圖、流程圖、時程表 | 接案時一次 |
| 追蹤單元 | 現場照片、檢驗報告、**簽收單掃描** | **每天** |
| 請款事件 | 發票、請款單 | 每次請款 |

**簽收單掃描是關鍵**：簽收是請款的依據。日後業主說「沒收到」，
系統裡有簽收人、日期、單號，**再加上那張單的照片**，爭議就結束了。

**權限不另外設一套**：附件的可見範圍＝它掛的那個東西的可見範圍。
看不到那個專案的人，連檔案存在都不知道。

**先不做**：資產、廠商。不是不需要，是短期內用不到——之後要加只是多兩行設定。

**改的成本**：低。

# 第五輪｜2026-08-13　實作附件與現金流時發現的

> 這三則不是規劃時想到的，是**做下去才看見的**。
> 都已經照下面的答案實作了，需要的話再改。

## D33　合約 PDF 誰看得到？

**問**：附件的可見範圍＝母物件的可見範圍（D32）。照這條做，
廠長看得到專案，所以下載得到業主合約。可以嗎？

**答**：**不可以。合約／發票類附件另外要求金額權限。**

廠長、採購、品保、倉管看得到專案，但**看不到合約金額**——這是既有的設計
（`scoping.can_view_amount`）。而合約 PDF 的第一頁就寫著合約總價。

> **欄位擋了、檔案沒擋，那道限制等於沒有。**

所以 `contract` 與 `invoice` 兩類：
- 不只擋下載，**在清單裡也不出現**
- 因為「有一個檔案但你不能看」一樣洩漏了「這個案子有合約」

**這是一整類容易漏掉的洩漏。** 日後加新的附件分類時要先問：
「這種檔案的內容，等於哪個受限的欄位？」

**改的成本**：低（一個常數集合）。若判斷太嚴，把某一類從清單移除即可。

## D34　核可付款與登錄付款要不要分開？

**答**：**分開。** 經營者核可、會計登錄付款。

| 動作 | 誰可以 | 意思 |
|---|---|---|
| 核可（待計價 → 已核可） | **只有經營者** | 「這筆該付、金額對」 |
| 登錄付款（已核可 → 已付款） | 經營者、會計 | 「錢已經匯出去了」 |

跟收款側的職能分離同一個道理：**同一個人不該既決定要付多少、又執行付款。**

這條在小公司會有點麻煩——老闆不在就核可不了。若要放寬，
把 `approve_payable` 加上專案負責人即可（`main/utils/permissions.py` 一行）。
但**放寬之前先想清楚**：那等於專案負責人可以自己決定付給包商多少錢。

**改的成本**：中（權限改一行，但制度上的意義要想清楚）。

## D35　應付與現金流要不要各占一個分頁？

**答**：**合成一個分頁「應付付款」**，裡面兩個子頁。

導航最多 6 個分頁是硬規定（D09）。現在已經有 8 個，
再加兩個就變 10 個——而且「應付款項」與「現金流預測」
本來就是同一件事的兩個尺度：一筆一筆看，跟加總起來看未來哪週會缺。

會計本來就是看完清單再看總表，中間不該隔一次導航切換。

**採購看不到現金流的子頁**——不是 disable，是不出現。
那是全公司的資金狀況，不是他的範圍。

**改的成本**：低。

# 第三輪｜2026-08-02　實際操作後的修正

## D22　完成度是「整批累計」還是「這一站」？ ⚠️

**問**：追蹤單元有九個階段，也有一個完成度數字。這兩者是什麼關係？

**答**：完成度是**目前這一站**的完成度，換站歸零重算。

24 支鋼柱在「加工」做完 24 支，推進到「品檢」後歸零——因為要重新檢 24 支。
每一站都要對這 24 支做一次事，「加工完成」不代表「品檢也完成」。

**這是一個已修正的錯誤。** 修正前完成度跨階段累計，結果是第二站起一進站就顯示 100%，
這個欄位等於作廢。修正後：

- 推進時完成度歸零
- 舊值寫進階段歷程的 `qty_at_exit` / `pct_at_exit`，永遠查得回來
- 卡片與面板的標籤明寫「『加工』完成 20 / 24 支」

**刻意不做的事**：不提供「整體百分比」。九站工作量差很多（加工兩週、置料區放著不動），
等權重平均會得到一個看起來精確、實際上騙人的數字。
整體進度就看階段軌道（第 3 / 9 站）。

> 詳見 `員工手冊.md` §1

**改的成本**：中。要改回累計制的話，`stage_service.move_stage()` 拿掉歸零那幾行即可，
歷程欄位留著不影響。

## D23　「追蹤單元類型」能不能由管理員自己增加？

**問**：新增追蹤單元時類型是寫死的，能不能讓系統管理員自己 CRUD？

**答**：**改成選「階段模板」，模板由管理員在 Admin 自建。**

原本前端寫死兩個選項（構件批次／土建工項）。現在改成：

```
使用者選的是「階段流程」
  ├─ 構件批次（用數量計進度）
  │    └─ 鋼構構件批次（9 站）· 預設
  └─ 土建工項（用百分比計進度）
       └─ 土建工項（5 站）· 預設
```

在 Admin 建一條「鋼構－免表面處理（7 站）」，它立刻出現在下拉裡——
**加流程不用改程式、不用重新部署**。

`unit_type` 由模板的 `applies_to` 自動推導，使用者不必也不該自己選：
選了土建模板卻標成構件批次，進度就會用錯的算法。

**保留為程式碼的**：進度算法（數量 vs 百分比）本身。那是數學不同，不是設定問題。

**額外規則**：已經有階段異動紀錄的追蹤單元**不准換模板**。
中途換軌會讓歷程對不上、請款觸發條件跟著錯。要換就建新的。

**改的成本**：低。

## D24　庫存數量可不可以直接修改？

**問**：資產的部分要怎麼自行新增？

**答**：可以新增，但**數量只能透過三種異動改變**——入庫（+）、盤點調整（±）、領用出庫（−）。
API 層直接把 PATCH／PUT 關掉（回 405）。

理由：直接 UPDATE 數字是最容易做的，也是最容易在半年後變成
「帳面 300 支、實際 180 支，沒人知道那 120 支去哪」的做法。

**盤點調整必須填原因**。帳實不符是管理問題，讓人隨手改而不用交代，等於承認帳沒在管。

**改的成本**：低（但不建議改）。

## D25　資產要放到多廣？需不需要另做倉儲系統？

**問**：這裡的資產適合把公司所有設備、機械、材料都放進來嗎？不然是不是要再做一個倉儲系統？

**答**：**不需要另做一套，這個就是。** 但要分清楚兩種東西，且不是什麼都放。

分兩種管（問的問題不同）：

| | 工具／設備 | 建材／零件 |
|---|---|---|
| 問的問題 | 在誰手上 | 還剩多少 |
| 單位 | 一台（財產編號） | 一批（批號） |

**放**：設備、工具（校驗到期會影響驗收）、建材、有安全存量的耗材
**不放**：辦公文具、一次性低值耗材、**車輛**（里程油耗保險駕駛是另一套領域模型，P3 再議）、不動產

判準：**這個東西找不到／壞了／過期了，會不會影響工程進度或驗收？**

缺的不是系統，是採購流程那一段（請購→詢比議→採購單→收料），P2 才做。
再做一套會出現兩份庫存數字，然後永遠對不起來。

> 詳見 `員工手冊.md` §3

**改的成本**：低（要納入車輛的話是 P3 的新模組，不是改現有的）。

## D26　主檔要在哪裡維護？

**問**：專案類型、客戶名單、負責人名單能不能在前端改，不要跳到 Django Admin？

**答**：**把客戶、廠商、員工搬到前端的「設定」分頁**；其餘留在 Admin。

原本一律走 Admin（決策 T03）。實際使用後推翻一半——判準是**動的頻率**：

| 主檔 | 在哪維護 | 為什麼 |
|---|---|---|
| 客戶 | **前端** | 每接一個新案就要建，老闆與行政每週都動 |
| 廠商 | **前端** | 同上 |
| 員工與角色 | **前端** | 到職離職、換部門、調角色是常態 |
| 物品（規格尺寸材質） | Admin | 欄位依料型不同（鋼板問厚寬長、H型鋼問腹板翼板），Admin 的表單處理得比自己刻的好 |
| 位置階層 | Admin | 倉庫儲位建一次就不太動 |
| 階段流程 | Admin | 定案後極少改；改動影響全公司，該有點摩擦力 |

**專案類型（土建／鋼構／混合）維持寫死**。它只有三種，而且決定底下能建哪種追蹤單元——
那是結構性分類，不是設定值。

權限給 `manage_masters`，開放給**經營者**與系統管理員。
為了改一個客戶電話要去找系統管理員，制度上不合理。

**兩條保護規則**：
- 有案子的客戶、被引用過的廠商**不可刪除**，只能停用——刪掉會讓歷史資料失去參照
- 員工**完全不提供刪除**（API 回 405）。他做過的推進、簽收、請款異動都掛在他名下，刪了歷史就斷了

**改的成本**：中。

## D27　「期別」是什麼？

**問**：在追蹤看板點編輯時會看到期別。這是整個專案的分期付款期別，還是單一追蹤內容？

**答**：是**工程的分期（標段）**，不是分期付款——雖然兩者常常對得起來。

它做兩件事：
1. 把追蹤單元分組（第一期的批次歸第一期）
2. **決定簽收時觸發哪一筆請款里程碑**

合約寫「第一期構件全數簽收後請款 40%」時，系統要知道「哪些批次算第一期」——靠的就是這個。
里程碑也可以綁期別，兩邊對上了，簽收才會觸發正確的那一筆。

沒有分期的專案，里程碑就以**全案**為範圍，一樣能運作。

**同時修掉三個問題**：
- 期別原本只能在 Admin 建 → 現在在**專案頁展開該案**就能建
- `TrackingDetail` 沒有回傳 `phase` 的 id → **編輯追蹤單元時期別會被清成 null**（真的 bug）
- 沒有分期的專案，表單只是不顯示期別欄位，使用者不知道為什麼 → 現在會說明並指路

**改的成本**：低。

## D29　土建工項永遠觸發不了請款 ⚠️

**問**：里程碑用「該期全部簽收」，但追蹤單元是土建的話，土建完全都不用簽收，
永遠觸發不了，怎麼辦？

**答**：**「監造查驗」就是土建的簽收站。** 已把它改成 ✍＋💰。

### 這是一個真的 bug

決策 D14 說「監造查驗通過即可計價」。實作時把它理解成**「不需要簽收」**，
所以土建流程五站全都沒有 `requires_signoff`。結果是：

```
四種請款觸發方式，三種靠 signoff_date 判斷
土建工項永遠沒有 signoff_date
→ 土建案的里程碑永遠卡在「還差 N 批」，而且畫面上看不出原因
```

**正確的理解**：查驗通過**就是**業主方認可這件事完成了，
跟鋼構的「業主簽收」是同一個概念，只是簽的人是監造、簽的是查驗記錄表。

### 改了什麼

```
之前  放樣定位 → 施工中 → 自主檢查 → 監造查驗 → 完成 💰
現在  放樣定位 → 施工中 → 自主檢查 → 監造查驗 ✍💰 → 完成
```

跟鋼構完全對稱（出貨進場 → 進場簽收 ✍💰 → 安裝 → 收尾）。

### 同時補上防呆

「請款設定檢查」原本只看整個專案有沒有需簽收的站，而且只是 ⚠️。
改成**按里程碑的實際範圍判斷**，並升級為 ✘ **必須處理**：

```
✘ 流程含「需簽收」站
  「第一期請款」涵蓋的 3 個單元走「土建工項」，這條流程沒有需簽收的站
  為什麼：那些單元永遠不會有簽收日期——里程碑會永遠卡在「還差 N 批」，
         而且看不出原因
  該做的：① 到 Admin 把該流程的驗收站勾「需簽收」（土建建議勾在「監造查驗」）
         ② 或把這筆里程碑改成「手動」，由會計自己按
```

**改的成本**：中。已建立的土建工項若已經走過「監造查驗」，
需要退回該站再登錄簽收一次（或由會計走手動請款）。目前尚未上線，無實際資料受影響。

## D17　完成度基準 ⚠️

**問**：「一定的完成度」要用什麼算？

| 選項 | 說明 |
|---|---|
| **✅ 重量（噸數）** | 鋼構本來就論噸計價，物品主檔已有單位重量可自動換算，與業主對帳最容易 |
| 數量（支／組） | 簡單，但一支小梁與一支大柱算同一支，與實際價值不成比例 |
| 金額（報價小計） | 最準確，但需在每批構件上記錄報價金額（資料模型要加欄位） |
| 人工判定 | 系統只顯示簽收狀況，由人自行判斷 |

**答**：**重量（噸數）**

**公式**：
```
分批請款金額 = 里程碑金額 × (該批 total_weight_kg ÷ 該期總噸數)
累計完成度   = 已簽收噸數 ÷ 該期總噸數
```

**因此新增欄位**：`TrackingUnit.total_weight_kg`（該批總重量）。**沒填這個欄位，`weight_threshold` 與 `per_batch` 兩種觸發方式就算不出來。**

| T05 | 回退階段必填原因分類 | 這是 P3 品質失敗成本（PAF 模型）的資料來源。P1 就開始收集，P3 才有一年歷史可分析 | 低 |
| T06 | 無權限的資料回 404 而非 403 | 不讓人從錯誤碼推測「有這筆資料但我看不到」 | 低 |
| T07 | 進度回報支援 `delta` 增量 | 兩個師傅同時回報 +5，用增量會正確加 10；用絕對值後者會覆蓋前者少算 5 支 | 低 |
| T08 | 廠商用一張表 ＋ 類型陣列 | 「全興噴砂廠」可能同時是外包加工廠與供應商。分四張表會重複建檔、統編對不起來 | 中 |
| T09 | KPI 每日排程算好存快照 | 即時聚合會掃全表，8GB 撐不住；KPI 本來就是趨勢指標不需秒級即時 | 低 |
| T10 | 「無資料」不等於「不好」 | 沒排產的設備 OEE 顯示「無資料」而非 0%，否則公司平均會被錯誤拉低 | 低 |
| T11 | 附件經 Django 檢查權限才送出 | 不能讓 nginx 直接服務靜態檔，否則任何人拿到 URL 就能下載合約 | 低 |
| T12 | 系統參數帶生效日期 | 手冊 13.5 明指「費用率不更新」是三大核算陷阱之一。歷史訂單要用當時的費用率核算 | 低 |
| T13 | 業務邏輯全部放 `services/` | `move_stage()` 這類有副作用的操作要能被 API、Django Admin、排程三方共用。邏輯只有一份，不會出現「前端能做但後台不能」的落差 | 低 |
| T14 | 餘料的 `parent_lot` 用 PROTECT 而非 SET_NULL | **W2 實作時被自己寫的 CHECK 約束擋下才發現**：SET_NULL 會讓餘料的來源變 NULL，違反「餘料必須有來源批號」。實際意義是刪掉母批號等於切斷材質證明的追溯鏈，本來就不該允許 | 中 |
| T15 | `select_for_update(of=("self",))` | 不加的話，`select_related` 到 nullable 外鍵會產生 LEFT JOIN，PostgreSQL 不允許對 outer join 的 nullable 側加鎖 | 低 |
| T16 | 限流計數用 LocMemCache 而非資料庫 | 原本每個 API 請求都多打一次 DB，且資料庫一斷連 Swagger 都 500。代價是實際上限變成「設定值 × worker 數」，對內部系統可接受——暴力破解本來就由 django-axes 另外擋 | 低 |
| T17 | Admin 暫時保留操作按鈕 | 前端完成前，讓使用者能實際跑一次完整流程驗證邏輯。呼叫的是與 API 相同的 service 函式。**W7 完成後保留為管理員後備手段**（見 T24） | 低 |
| T18 | 看板不分頁，但強制指定範圍且上限 300 張卡 | 分頁的看板沒有意義——看板的價值就是「一眼看完哪一欄比較高」。但無上限查詢在 8GB 主機上是不能開的門，因此改成兩道硬限制：必須指定專案或類型、超過 300 筆回傳計數並要求縮小範圍 | 中 |
| T19 | 儀表板階段分布**依模板分組**，不合併 | 鋼構的「加工」與土建的「施工中」都是第 2 站。混在一起數會得到一個沒有意義的數字——那不是同一件事。實作初版曾犯這個錯，實測時發現 | 低 |
| T20 | 金額欄位無權限時回 `null`，不是 `0`，不是省略欄位 | `0` 是一個會被誤信的數字；省略欄位會讓前端不知道是「沒有」還是「不給看」。`null` ＋ 前端顯示 `──` 三者語意最清楚 | 低 |
| T21 | 變更操作回傳完整副作用（warnings／next_action／status_changed／billing） | 推進一個階段可能同時觸發請款、轉為待簽收、把狀態改成「注意」。這些副作用如果不講，使用者只會看到畫面閃一下，然後在月底對帳時才發現有筆錢自己冒出來 | 中 |
| T22 | 快速回報按鈕的級距**由後端算**（噸 0.5/1/5、支 1/5/10） | 前端不寫「如果單位是噸就…」。日後要加單位或調級距，只改後端一處 | 低 |
| T23 | 前端除「我的工作」外全部 lazy 載入 | 現場人員只會用到那一頁，沒必要讓他的手機下載儀表板與看板的程式碼。實測首屏 gzip 103 KB，各畫面另外 2–3 KB | 低 |
| T24 | 保留 Admin 的操作按鈕（推翻 T17 的「應移除」） | 前端完成後重新評估：這組按鈕呼叫的是同一組 service 函式，維護成本近乎零，卻是前端出問題時管理員唯一的補救手段。**移除它省不到什麼，留著多一條退路** | 低 |
