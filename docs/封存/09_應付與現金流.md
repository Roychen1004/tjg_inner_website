> 操作說明在 [員工手冊.md](../員工手冊.md) Part 3。這份文件保留設計理由。
>

## 1. 要解決什麼

> 「三月要付中鋼的料款、要付永固的計價、要付全興的噴砂費——**加起來多少？帳上夠不夠？**」

現在答不出來。系統只知道**錢什麼時候進來**（請款事件），完全不知道**錢什麼時候出去**。

一半的現金流不叫現金流。

### 具體的痛

| 情境 | 現在會發生什麼 |
|---|---|
| 月中要不要接下一個案子 | 憑感覺。不知道下個月要付多少 |
| 業主拖款兩個月 | 到了要付分包商那天才發現週轉不過來 |
| 這個案子到底賺不賺 | 收入知道（合約額），成本散在各處，算不出來 |
| 分包商來問「什麼時候付」 | 翻紙本合約找付款條件 |

## 3. 範圍：只管工程案的大型花費（決策 D31）

| 進系統 | 不進系統 |
|---|---|
| **材料採購**（中鋼鋼板、H型鋼、螺栓…） | 薪資 |
| **分包工程**（土建包商計價） | 租金、水電 |
| **外包加工**（噴砂、鍍鋅、熱處理） | 辦公費用、稅金 |
| **運輸**（板車、吊車） | 保險、貸款 |

**這是「專案現金流」不是「公司現金流」。** 差別要講清楚，否則會誤以為
這個數字就是公司帳上的錢——它不是，它少了每月固定支出。

> 好處是範圍明確、資料來源都在工程流程裡，**不必等薪資模組（P4）就能用**。
> 代價是預測偏樂觀。畫面上會明說這一點（見 §7.4）。

## 4. 核心設計：跟收款側對稱

這是整個設計最重要的一句話：

> **應付的結構跟應收一模一樣，只是方向相反。**

```
應收（已經有）
  專案（跟業主的合約）
    └─ 合約里程碑（合約寫的請款條件）
         └─ 請款事件（實際能請的錢）  可請款 → 已請款 → 已收款

應付（要做）
  分包合約（跟包商的合約）    ← ★ 就是你說的「專案那邊新增跟包商合作的付費金額」
    └─ 應付款項（實際要付的錢）  待計價 → 已核可 → 已付款
```

**為什麼要對稱**：學會一邊就等於學會另一邊。
會計看請款事件的操作邏輯，跟看應付款項一模一樣——狀態往前推、往回轉要填原因、
每一步留不可竄改的歷程。**少學一套東西。**

### 4.1 為什麼應付只有兩層、應收有三層

應收之所以要三層，是因為 `per_batch` 觸發時**一條里程碑會生出 N 筆錢**。

應付沒有這種自動觸發——包商送計價單過來，我們建一筆。
所以 `分包合約 → 應付款項` 兩層就夠：合約管「總共多少、什麼條件」，
應付款項管「這次要付多少、哪天付」。

## 5. 資料模型

### 5.1 `Subcontract` 分包合約（新）

**掛在專案底下**，跟 `Project` 對稱——`Project` 是業主付我們，`Subcontract` 是我們付別人。

| 欄位 | 說明 |
|---|---|
| `project` | 屬於哪個案子（**算專案成本的關鍵**） |
| `vendor` | 哪一家廠商 |
| `code` | 系統編號 `SC-YYYY-NNN` |
| `title` | 如「B區土建工程」「第一期鋼材採購」 |
| `category` | 分包工程／材料採購／外包加工／運輸 |
| `contract_amount` | 合約金額（未稅） |
| `payment_term_type` | 月結／請款日起算／驗收後起算 |
| `payment_term_days` | 天數（30／60／90） |
| `retention_pct` | **保留款百分比**（見下） |
| `status` | 進行中／已完工／已結案 |
| `note` | 備註 |

> **保留款**：台灣營造業常見「每期扣 5–10%，驗收合格後退還」。
> 不模型化的話，每期實付金額會算錯 5–10%——一個 500 萬的分包合約就差 25–50 萬。

### 5.2 `Payable` 應付款項（新）

| 欄位 | 說明 |
|---|---|
| `subcontract` | 屬於哪張合約（**可空**——零星運費、小額採購不必先開合約） |
| `project` | 一定要有 |
| `vendor` | 一定要有 |
| `category` | 同上四類 |
| `title` | 如「第三期計價」「2月份鋼材」 |
| `amount` | 未稅金額 |
| `tax_amount` | 稅額（見 §8 待確認） |
| `retention_amount` | 本次扣的保留款 |
| `payable_amount` | **實付金額**＝amount ＋ tax − retention |
| `state` | `pending` 待計價 → `approved` 已核可 → `paid` 已付款 |
| `due_date` | **預計付款日**（由付款條件推算，可覆寫） |
| `paid_date` | 實際付款日 |
| `payment_method` | 匯款／支票（見 §8 待確認） |

加一張 `PayableLog`（不可竄改的狀態歷程），跟 `BillingClaimLog` 對稱。

### 5.3 收款側要補的

| 補在哪 | 欄位 | 為什麼 |
|---|---|---|
| `Customer` | `payment_term_type`＋`payment_term_days` | 才推得出預計收款日 |
| `BillingClaim` | `due_date` 預計收款日 | 請款日 ＋ 客戶帳期，可覆寫 |
| `BillingMilestone` | `expected_claim_date` 預計可請款日 | 未到期的里程碑要落在時間軸上的哪一格 |

> `expected_claim_date` 由使用者填。**不自動從工期推算**——
> 「第一期什麼時候會全部簽收」是專案負責人的判斷，系統推不出來。
> 系統推得出來的東西才自動算，推不出來的就問人，**不要假裝知道**。

## 6. 日期怎麼推算

### 6.1 收款

| 狀態 | 預計收款日 | 確定性 |
|---|---|---|
| 已請款 | `invoice_date` ＋ 客戶帳期 | **高**——單已開，等收 |
| 可請款 | 今天 ＋ 開單作業天數（預設 3 天）＋ 帳期 | 中——還沒開單 |
| 未到期 | `expected_claim_date` ＋ 帳期 | **低**——條件還沒達成 |

**月結的算法**：「月結 60 天」＝ 請款當月月底 ＋ 60 天。
1/15 請款 → 1/31 結帳 → **4/1 收款**。不是 3/16。這個差兩週。

### 6.2 付款

| 狀態 | 預計付款日 | 確定性 |
|---|---|---|
| 已核可 | 計價日 ＋ 合約帳期 | **高** |
| 待計價 | 預估計價日 ＋ 帳期 | 中 |
| 合約剩餘未計價 | 依工期均攤到剩餘月份 | **低** |

## 7. 現金流預測畫面

### 7.1 一個畫面回答一個問題

> **未來哪個月會缺錢？**

不是「顯示所有財務資料」。是**找出累計淨額跌破零的那一格**。

### 7.2 版面

```
現金流預測                    [ 未來 12 週 ▾ ]  [ 全部專案 ▾ ]

           8月2週  8月3週  8月4週  9月1週  9月2週  9月3週
──────────────────────────────────────────────────────────
 收入       240萬     0    180萬     0     320萬     0
   確定      240萬     0      0       0       0       0
   很可能      0       0    180萬     0       0       0
   預估        0       0      0       0     320萬     0

 支出       -85萬  -120萬  -40萬  -260萬   -95萬   -30萬
──────────────────────────────────────────────────────────
 淨額      +155萬  -120萬 +140萬  -260萬  +225萬  -30萬
 累計      +155萬   +35萬 +175萬  ⚠ -85萬 +140萬 +110萬
                                    ↑
                              9月1週會缺 85 萬
```

**⚠ 那一格是整個畫面的重點。** 其餘都是為了讓那一格可信。

### 7.3 確定性分級

**混在一起會得到一個看起來精確、實際上騙人的數字**（跟「整體完成度」不做的理由一樣）。

| 等級 | 收入 | 支出 |
|---|---|---|
| **確定** | 已請款，等收 | 已核可，等付 |
| **很可能** | 可請款，只差開單 | 已計價，待核可 |
| **預估** | 未到期里程碑（日期是人填的） | 合約剩餘額均攤 |

畫面上可以**只看「確定」**——那是最壞情況下的現金流。

### 7.4 誠實標註

畫面底部固定一行：

> ⚠️ 這是**專案現金流**，不含薪資、租金、水電等固定支出。
> 公司整體現金部位請再扣掉每月固定成本。

不寫這句，看的人會以為累計是正的就沒事。

### 7.5 點進去看明細

任何一格點下去，列出構成它的每一筆：

```
9月1週 支出 -260萬
  永固土木包商  B區土建第三期計價   -180萬  已核可  9/3 付
  中鋼鋼鐵      2月份鋼材            -65萬  已核可  9/5 付
  大發板車運輸  8月運費              -15萬  待計價  9/6 付（估）
```

**沒有明細的總數沒有人敢信。**

## 8. 待確認（會影響數字對不對）

| # | 問題 | 為什麼重要 | 建議 |
|---|---|---|---|
| **B1** | **支票票期** | 台灣營造業大量用支票。開票日 ≠ 兌現日，中間可能還有 60–90 天。**不模型化的話現金流會早算兩三個月** | ✅ 已做：`payment_method` ＋ `check_due_date`，現金流用 `cash_date`（支票看兌現日）。**選了支票沒填票期時，畫面會警告** |
| **B2** | **含稅還是未稅** | 請款單開的是含稅金額，實際進出的錢也是含稅。但合約額通常談未稅 | ✅ 已做：金額欄位存未稅，**現金流一律 ×1.05**，畫面底部標明。損益則用未稅（稅是代收代付，不是賺的） |
| **B3** | 保留款比例 | 每期扣 5–10%，不算的話每筆都高估 | ✅ 已做：合約層級設 `retention_pct`，計價時自動帶、可逐筆覆寫 |
| **B4** | 客戶帳期實際怎麼談 | 影響所有收款日 | ⚠️ **仍待確認**。示範資料用固越 月結 60、統一 月結 30、國工局 驗收後 45 |
| **B5** | 分包商付款條件 | 同上 | ⚠️ **仍待確認**。示範資料用月結 30／60 |
| **B6** | 要不要做「專案損益」 | 有了應付就算得出 | ✅ 已做：專案頁一個區塊，已計價／已簽約兩個口徑 |

> ⚠️ **B1 與 B2 是照「建議」做的，不是照你確認過的做法做的。**
>
> 程式已經支援支票票期與含稅換算，但**實際上你們的票期多長、
> 業主與分包商的帳期怎麼談，這些數字還沒對過**。
> 對不上的話，表上的日期跟金額都會偏——而且偏得很有說服力。
>
> **要對的只有三件事**（見下），對完把數字填進客戶與分包合約的欄位就好，
> 不需要改程式。

### 需要你提供的三件事

1. **三、五份實際的分包合約** —— 看付款條件怎麼寫（月結？請款日起算？幾天？保留款幾 %？）
2. **業主合約的付款條件** —— 每個客戶各自的帳期，填進「設定 → 客戶」
3. **支票的票期大概多久** —— 開票後幾天兌現，以及大概多少比例的付款是用支票

前兩件填進系統就好。第三件如果比例很高（超過一半），
現金流的預設值可能要調——現在是「沒填票期就用開票日算」，偏樂觀。

## 9. 權限

跟金額有關的東西，可見範圍跟請款側一致。

| 動作 | 經營者 | 專案負責人 | 會計 | 廠長 | 採購 |
|---|:--:|:--:|:--:|:--:|:--:|
| 看現金流預測 | ✔ | ✘ | ✔ | ✘ | ✘ |
| 看專案的應付 | ✔ | ✔（自己的案） | ✔ | ✘ | ✘ |
| 建分包合約 | ✔ | ✔ | ✘ | ✘ | ✘ |
| 建應付款項（計價） | ✔ | ✔ | ✔ | ✘ | ✔ |
| **核可付款** | ✔ | ✘ | ✘ | ✘ | ✘ |
| 登錄已付款 | ✔ | ✘ | ✔ | ✘ | ✘ |

> **核可與登錄付款分開**（跟收款側的職能分離同理）：
> 同一個人不該既決定要付多少、又執行付款。

**現金流預測只給經營者與會計**——那是全公司的資金狀況，
專案負責人只需要看自己案子的損益。

## 9b. 實作時發現的四件事

### 9b.1 「沒填」與「填 0」是兩件事

保留款與稅額都有「留空＝系統自動算」的設計。用 `if not value` 判斷有沒有填，
會把**明確填的 0 也當成沒填**然後覆蓋掉——免稅的項目被硬加 5%、
不扣保留款的項目被硬扣，而且沒有任何錯誤訊息。

改用「這個欄位有沒有出現在請求裡」判斷。免稅、零稅率、國外廠商都是真實存在的情況。

### 9b.2 權限要在業務規則之前檢查

原本先檢查「往回轉必須填原因」再檢查權限。結果是**沒有權限的會計收到
「請填原因」**——等於告訴他「填了就能過」，而其實不能。

順序改成權限先行。這條適用於所有具名 action。

### 9b.3 資料庫的 CHECK 會變成 500

`paid_date >= billing_date` 有 DB 層的 CHECK 擋著。但使用者填錯日期時
收到的是「系統發生錯誤，請聯絡管理員」——他不知道自己填錯了哪一格。

DB 約束是**最後一道防線，不是錯誤訊息**。凡是使用者填得出來的違規，
都要在 view 層先擋一次，並說清楚是哪一欄、為什麼。

### 9b.4 空的格子本身就是資訊

現金流的時間軸是**先產生格子、再往裡面放錢**，不是照資料的日期分組。
照資料分組的話，沒有任何款項的那一週會整格消失——時間軸看起來是連續的，
實際上跳過了幾週。

同理，落在時間窗外的金額要另外列出來（`outside_window`）。
不列的話，使用者會以為表上的總額就是全部。

## 11. 做的順序（已完成）

```
① 分包合約 ＋ 應付款項（基礎資料）      ✅
② 收款側補預計收款日                    ✅
③ 現金流預測畫面                        ✅
④ 專案損益                              ✅
```

**沒有反過來先做畫面。** 沒有資料的預測畫面只會是一張空表，
而且會讓人以為「系統做好了但沒東西」——實際上是沒人輸入。

`seed_demo` 會建 4 張分包合約與 6 筆應付款項（含一筆支票），
所以新裝的系統一打開現金流就看得到東西長什麼樣，包含一個缺口。
