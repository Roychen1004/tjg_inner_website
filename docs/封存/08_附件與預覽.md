# 08 — 附件與預覽（規劃）

> 鐵正綱工程 內部管理系統
> 2026-08-05 規劃｜**2026-08-13 已實作**（W11）
> 操作說明在 [員工手冊.md](../員工手冊.md) Part 3。這份文件保留設計理由。

## 1. 要解決什麼

現在合約 PDF、施工圖、時程表全散在 LINE 群組、Email 附件、以及某台電腦的資料夾裡。

具體的痛：

| 情境 | 現在會發生什麼 |
|---|---|
| 業主爭議「當初圖不是這樣」 | 翻 LINE 往上滑，找到的可能是舊版 |
| 要對帳，找當初的簽收單 | 在誰的手機相簿裡？ |
| 新人接手一個案子 | 要問三個人才湊得齊圖說 |
| 工地拍了缺失照片 | 傳 LINE，兩週後被洗掉 |

**目標：跟這個案子有關的檔案，都在這個案子底下找得到。**

## 3. 掛在哪三個地方（決策 D32）

| 掛在 | 放什麼 | 誰會傳 | 頻率 |
|---|---|---|---|
| **專案** | 合約、施工圖、流程圖、時程表、變更文件 | 專案負責人 | 接案時一次，之後偶爾 |
| **追蹤單元** | 現場照片、檢驗報告、**簽收單掃描** | 工地主任、品保 | **每天** |
| **請款事件** | 發票、請款單 | 會計 | 每次請款 |

> **簽收單掃描為什麼重要**：簽收是請款的依據。日後業主說「沒收到」，
> 系統裡有簽收人、日期、單號，**再加上那張單的照片**，爭議就結束了。

**刻意先不做的**：資產（財產照片、校驗證明）、廠商（合約、證照）。
不是不需要，是**短期內用不到**——先把用得到的做好，之後要加只是多兩行設定。

## 4. 預覽策略（決策 D30）

### 4.1 硬限制

**瀏覽器只能原生顯示 PDF 與圖片。**

| 格式 | 能不能預覽 | 為什麼 |
|---|:--:|---|
| PDF | ✔ | 瀏覽器內建 |
| JPG / PNG | ✔ | 瀏覽器內建 |
| **XLSX** | ✘ | 要 LibreOffice headless 轉檔（+500MB） |
| **DWG** | ✘ | 要 CAD 轉檔引擎（更重，且多半要付費授權） |

裝轉檔服務會**直接撞破 8GB 的約束**（決策 D07）。不裝。

### 4.2 決定

**只預覽 PDF 與圖片，其餘明講要下載。**

```
┌─────────────────────────────────┐
│ 📄 固越案_工程合約.pdf    2.4 MB │
│    2026-01-15 · 張經理           │
│              [ 預覽 ]  [ 下載 ]  │
├─────────────────────────────────┤
│ 📐 1F平面圖.dwg          8.1 MB │
│    2026-02-03 · 張經理           │
│    這種格式無法在瀏覽器預覽，      │
│    請下載後用 AutoCAD 開啟        │
│                       [ 下載 ]  │
└─────────────────────────────────┘
```

**不做「假的預覽按鈕」**——按了跳出「無法預覽」比一開始就說清楚更糟。

### 4.3 為什麼這樣夠用

實務上的檔案分布：

```
合約、估價單、簽證、檢驗報告、施工說明   → PDF
現場照片、缺失記錄、簽收單掃描           → JPG
                                        ↑ 這些加起來超過九成，全部可預覽

施工圖原始檔                            → DWG（下載後用 CAD 開，本來就要）
時程表原始檔                            → XLSX（下載後用 Excel 開，本來就要）
```

**要看 CAD 圖的人，電腦裡本來就有 AutoCAD。** 在瀏覽器裡看一張沒有圖層、
不能量測、不能比對的縮圖，對他沒有用。

> **若日後想讓圖說一定看得到**：作法不是裝轉檔服務，而是規定
> 「上傳 DWG 時同時附一份簽核版 PDF」。那是流程問題，不是技術問題。

## 5. 權限設計

### 5.1 核心原則

> **附件的可見範圍＝它掛的那個東西的可見範圍。**

不另外設一套附件權限。看得到那個專案／批次／請款事件的人，
就看得到它的附件；看不到的人，連檔案存在都不知道。

| 母物件 | 誰看得到 | 依據 |
|---|---|---|
| 專案 | `scope_projects()` | 現場人員看不到專案清單 → 看不到專案附件 |
| 追蹤單元 | `scope_tracking_units()` | 現場人員只看得到指派給自己的 |
| 請款事件 | `scope_billing()` | 只有經營者、專案負責人、會計 |

**實作**：下載 view 先取母物件，套用對應的 scope function，
**取不到就回 404**（不是 403——不讓人從錯誤碼推測「有這個檔案但我看不到」，決策 T06）。

### 5.2 上傳與刪除

| 動作 | 誰可以 |
|---|---|
| 上傳到專案 | 有 `edit_project` 的人 |
| 上傳到追蹤單元 | 有 `edit_tracking` 的人（**含工地主任、廠長**） |
| 上傳到請款事件 | 有 `edit_milestone` 的人 |
| 刪除 | **上傳者本人**，或經營者 |

> **刪除為什麼要限制**：合約與簽收單是爭議時的依據。
> 讓任何有編輯權的人都能刪掉別人上傳的合約，是把公司的證據交給運氣。
>
> ⚠️ **待確認**：要不要改成「軟刪除」——標記為已刪除但檔案留著，
> 只有經營者看得到？成本低，但要多一個欄位與過濾條件。

### 5.3 下載路徑（決策 T11，已在架構文件）

```
瀏覽器 → GET /api/v0.1/attachments/<id>/download
              ↓
         Django view：檢查權限（套 scope function）
              ↓
         回傳 X-Accel-Redirect: /protected-media/attachments/2026/08/<uuid>.pdf
              ↓
         nginx 讀檔送出（Django 不碰檔案內容，記憶體不受影響）
```

⚠️ **絕不能讓 nginx 直接服務 `/media/`**——那樣任何人拿到 URL 就能下載合約。
`nginx.conf` 的 `/protected-media/` 已經標了 `internal`，外部打不進來。

## 6. 安全：副檔名不能信

現在 `Attachment.clean()` 只檢查副檔名。**副檔名是使用者說了算的。**

把 `evil.html` 改名成 `photo.jpg` 上傳，若日後有任何地方直接回傳這個檔案，
就是儲存型 XSS。

**要補三道**：

| 檢查 | 做法 |
|---|---|
| ① 真實類型 | 用 `python-magic` 讀 magic bytes，跟副檔名對得起來才收 |
| ② 回應標頭 | 下載一律帶 `Content-Disposition: attachment` ＋ `X-Content-Type-Options: nosniff` |
| ③ 圖片二次處理 | JPG/PNG 用 Pillow 重新編碼一次，**順便剝掉 EXIF**（含 GPS 座標） |

> ③ 還有一個好處：現場用手機拍的照片動輒 4–8MB，重新編碼並限制長邊 2000px
> 之後通常剩 300–600KB。**8GB 機器的磁碟不是無限的**，而且工地看照片是用手機
> 4G 連線，小檔案打開得快。

`python-magic` 需要系統套件 `libmagic1`，`Dockerfile` 要加一行。

## 7. 資料模型調整

`Attachment` 大致夠用，補三個欄位：

```python
category = models.CharField("分類", max_length=20, choices=AttachmentCategory.choices)
# contract 合約｜drawing 圖說｜schedule 時程｜photo 現場照片
# inspection 檢驗報告｜signoff 簽收單｜invoice 發票請款單｜other 其他

is_previewable = models.BooleanField("可預覽", default=False)
# 上傳時依實際 MIME 判定，前端不必再猜

checksum = models.CharField("SHA-256", max_length=64, blank=True)
# 同一份合約被傳兩次時看得出來；日後也可用於完整性驗證
```

**為什麼要 `category`**：專案底下可能有二十個檔案，
沒有分類就是一坨清單。有了分類，「合約在哪」是一次點擊而不是一次搜尋。

## 8. API

```
GET    /api/v0.1/attachments?target=project&id=12        列出某物件的附件
POST   /api/v0.1/attachments                             上傳（multipart）
GET    /api/v0.1/attachments/<id>/download               下載（X-Accel-Redirect）
GET    /api/v0.1/attachments/<id>/preview                預覽（inline，僅 PDF/圖片）
DELETE /api/v0.1/attachments/<id>                        刪除
```

上傳的 `target` 用 `{"target": "project", "id": 12}` 而不是直接給 ContentType id——
**不讓前端知道 ContentType 的內部編號**，那是資料庫細節。

## 9. 畫面

不新增分頁。**附件是掛在既有畫面上的一個區塊**（決策 D09：一件事一個入口）。

| 畫面 | 位置 |
|---|---|
| 專案頁 | 展開該案後，「期別」下面加一區「檔案」 |
| 追蹤單元面板 | 「查看異動歷程」旁邊加「檔案（3）」 |
| 請款事件卡片 | 有附件時顯示 📎 圖示，點開看 |

### 手機上傳

現場人員最常做的是**拍照上傳**。手機瀏覽器的 `<input type="file" capture>`
可以直接叫出相機，不需要 App。

```
┌──────────────────────┐
│ 第一期-1F鋼柱          │
│ ⋯                     │
│ 檔案 (2)              │
│  📷 缺失_焊道.jpg      │
│  📄 簽收單.pdf         │
│  [ 📷 拍照 ] [ 📎 選檔 ]│
```

## 10. 儲存與備份的影響

| 項目 | 估算 |
|---|---|
| 一個案子的合約＋圖說 | 20–50 MB |
| 現場照片（壓縮後 400KB × 每案 200 張） | 80 MB |
| **一個案子合計** | **約 100–150 MB** |
| 一年 10 個案子 | **約 1–1.5 GB** |

磁碟不是問題，但**備份時間會拉長**。`backup.sh` 用 `rsync` 增量同步 media，
所以只有新檔案會傳，影響有限。

> ⚠️ **要確認**：正式機的磁碟空間有多少？現在沒有記錄。
> 若只有 30–50GB，兩三年後要有清理或外接的計畫。

## 11. 實作時發現的三件事

規格沒寫、做下去才看見的。三個都留在程式碼的註解裡。

### 11.1 ⚠️ 合約 PDF 上面就寫著合約金額

原本的設計是「附件的可見範圍＝母物件的可見範圍」。照這條做，
**廠長下載得到業主合約**——他看得到專案，所以看得到專案的附件。

但廠長的角色本來就看不到合約金額（`scoping.can_view_amount`）。
**欄位擋了、檔案沒擋，那道限制等於沒有。**

修正：`contract` 與 `invoice` 兩類附件另外要求 `view_amounts`。
不只是擋下載——**在清單裡也不出現**，因為「有一個檔案但你不能看」
一樣洩漏了「這個案子有合約」。

> 這是一整類容易漏掉的洩漏：**權限設在欄位上，但同樣的資訊也存在於檔案裡。**
> 日後要加新的附件分類時，先問一句「這種檔案的內容等於哪個受限欄位？」

### 11.2 nginx 不會把 Django 的自訂標頭帶出去

用 X-Accel-Redirect 時，nginx 只轉發它認識的那幾個標頭。
`Content-Disposition` 會過，`X-Content-Type-Options: nosniff` **不會**。

Django 那邊看起來明明有設，實際回應裡沒有——而且不會有任何錯誤。
`nginx.conf` 的 `/protected-media/` 必須自己再設一次。

### 11.3 剝 EXIF 之前要先轉正

手機拍的照片是「橫著存、用 EXIF 標示要轉幾度」。直接剝掉 EXIF，
**照片會躺著**。要先 `ImageOps.exif_transpose()` 再存。

實測：3000×2000 的照片 1.2MB → 214KB，長邊降到 2000px，GPS 座標已移除。

| # | 問題 | 目前的做法 | 改的成本 |
|---|---|---|---|
